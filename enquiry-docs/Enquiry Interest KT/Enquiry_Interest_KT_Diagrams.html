Enquiry Interest

Enquiry Interest is a lightweight signal-capture endpoint: when a buyer shows interest in a supplier or product (a page view, a call-to-action click), a caller posts the context here. The API only validates and cleans the input, then publishes it to a RabbitMQ queue over an HTTP relay — it writes no database itself. A separate consumer persists the signal to a warehouse Postgres table through a stored procedure. It is a side pipeline, not part of the enquiry lifecycle, and is unrelated to the “intent” field Save Enquiry's personalization uses.

Behavioural Signals

Enquiry Interest

GET/POST /enquiry/enquiryInterest (before middleware.Validation; always binds a JSON body regardless of method). The sender GLID must be present and numeric; interest_query_ref_text == "||" is rejected as a fake request; lat / long containing letters or = is wiped; several fields are silently truncated. It then calls the HTTP relay pubapi.Insert_rabbitmq to publish to queue enquiry.post.intent on exchange ENQUIRY.topic; one retry, then a local file fallback. The ENQUIRY_INTEREST consumer defaults missing fields to "null" and calls sp_insert_iil_enquiry_interest_v4 on the imbldwhpg warehouse DB.

Business flowchart

A fire-and-forget interest signal

Capture, queue, persist — asynchronously:

  • Flow A — happy path: the caller posts the buyer id, product / category context, URL and geo; the API validates the sender id, cleans the payload, and publishes one queue message, then responds immediately. A consumer later inserts the row into the warehouse.
  • Flow B — validation failure: a missing or non-numeric sender id, or the "||" fake-request marker, is rejected before anything is queued.
  • Flow C — queue outage: if the RabbitMQ publish fails twice, the payload is written to a local fallback file and the caller still gets a success-shaped response.
  • Flow D — consumer: a message whose sender id resolves to "null" is dropped; a duplicate is detected by the stored procedure and acknowledged; a DB error drops the message with no retry.

Sequence diagram · Flows A + C

A signal queued, and the RabbitMQ-failure fallback

A queued signal and the outage fallback:

  1. A caller posts the interest context; the API validates the sender id and screens for the fake-request marker.
  2. It cleans geo and length, then publishes one message to enquiry.post.intent and responds immediately.
  3. alt — publish succeeds: the consumer later inserts the row into the warehouse via the stored procedure; publish fails twice: the payload is written to a local fallback file and the caller still gets a success-shaped response.

Glossary

Business terms used above.

The signal

Enquiry interest
A captured buyer interaction — a listing view, a call-to-action click — that is not itself an enquiry. Raw behavioural data for analytics / personalization / lead scoring.
Fire-and-forget
The API validates, cleans and publishes to a queue, then responds. The caller learns only whether the message was queued, never whether the DB insert succeeded.
interest_type / modreftype / login mode
Opaque numeric classification codes owned by the calling team; no enum for them exists in either repo.
Not Save Enquiry's “intent”
Save Enquiry's personalization inspects an intent field for leap@indiamart.com; that is a different concept that merely shares the English word.

Validation

Mandatory sender id
interest_sender_glusr_id must be present and numeric, or the request is rejected before anything is queued.
"||" fake-request
A ref-text of exactly || is treated as bot / garbage and rejected.
Geo sanitation
If either latitude or longitude contains a letter or =, both are wiped rather than storing garbage coordinates.
Silent truncation
ModID to 8 chars, URLs to 500, ref-text to 250, product name to 200 — over-length values are cut, not rejected.

Transport & storage

enquiry.post.intent
The RabbitMQ queue (exchange ENQUIRY.topic) the signal is published to, via an HTTP publish relay rather than a native AMQP client.
File fallback
If the publish fails after one retry, the payload is written to a local log file for later (manual / TD-agent) reprocessing; no replay cron was found.
ENQUIRY_INTEREST consumer
Persists the signal to the warehouse via sp_insert_iil_enquiry_interest_v4; defaults missing fields to "null", drops null-sender messages, and treats a stored-proc duplicate as a successful no-op.
No retry on DB error
A consumer-side DB failure nacks the message without requeue and with no visible dead-letter queue — the signal is lost.
imbldwhpg
The warehouse Postgres database the interest rows land in.
