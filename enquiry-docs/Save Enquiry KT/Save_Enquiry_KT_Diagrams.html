Save Enquiry

Save Enquiry is the one write endpoint that permanently creates every buyer enquiry, from any channel — web, app, WhatsApp, catalogue page, third-party. It validates and cleans the input, screens the requirement text for banned / spam keywords (skipped for auto-generated “templated” text), writes through a stored procedure that also decides a QueryDestination (visible now, hold, or reject), and then fires one bundled message that fans out to Lead Management, Personalization and the WhatsApp / preferred-channel pipeline. A backup file plus a daily replay cron makes sure nothing is lost if the save or the fan-out fails.

Lead Capture

Save Enquiry

GET/POST /enquiry/saveEnquiry. Struct validation applies truncate / numeric tags and UTF-8 cleaning; a missing or invalid sender / receiver id short-circuits with queryid = -2 and no DB call. Three parallel lookups (receiver, sender, product) precede CheckBannedKeyword (external BAN API, skipped for templated text); a hit forces InForceDestination = 2, WaitingreasonId = -999. The core write is select sp_insert_iil_enquiry_v32(…) (~70 params, 2-second timeout); on failure a backup JSON is written. Success publishes one ENQ_DATA RabbitMQ message; the controller remaps destination 8 / 9 → 3 and code 430 → HTTP 200.

Business flowchart

The single choke-point for every enquiry

One endpoint, several branches:

  • Flow A — happy path: validate, look up sender / receiver (and product, if only a reference id was sent), screen the text, write, and notify Lead Management, Personalization and the preferred-channel worker in the background.
  • Flow B — banned keyword: a spam / abuse match still saves the enquiry, but routes it to a non-visible waiting state (destination 2, reason -999).
  • Flow C — templated text: an auto-filled generic requirement skips the BAN API entirely.
  • Flow D — product auto-fill: a catalogue enquiry with only a product reference id has the product name fetched and attached.
  • Flow E — guardrail: a missing sender / receiver id is rejected before any DB round-trip (queryid = -2, returned as HTTP 200).
  • Flow F — recovery: if the save or the fan-out fails, the whole request is written to a backup file and a daily cron replays it.

Data-flow diagram · Level 1

Where an enquiry is created and fanned out

A lean write, a wide fan-out:

  • 1.0 Validate & enrich cleans input and runs three parallel reads against D1.
  • 2.0 Screen calls the external BAN API unless the text is templated.
  • 3.0 SP write calls sp_insert_iil_enquiry_v32 and gets back a QueryDestination.
  • 4.0 Fan-out publish sends one bundled ENQ_DATA message; a downstream consumer splits it to FENQ, LMS and Personalization queues, which reach D2–D3, a Kafka topic and a Redis queue.
  • 5.0 Backup writes a JSON file on failure; the replay cron POSTs it back to this endpoint.

Sequence diagram · Flows A + B

A normal save, with the banned-keyword branch and downstream fan-out

A normal save with the spam branch shown:

  1. A client posts the enquiry; the API validates and resolves sender / receiver ids (missing → queryid = -2, no DB call).
  2. Three parallel lookups enrich the payload.
  3. alt — text present and not templated: the BAN API is called; a hit sets destination 2 / reason -999. Templated or empty: screening is skipped.
  4. The stored procedure writes the enquiry and returns a destination; one ENQ_DATA message is published and the consumer fans it out to Lead Management, Personalization and the preferred-channel worker.

Glossary

Business terms used above.

The write

Enquiry
A buyer's expression of interest in a supplier's product or service — IndiaMART's core lead unit.
sp_insert_iil_enquiry_v32
The stored procedure that actually creates the enquiry (~70 parameters). The tables it writes live inside the SP, not in the API code.
QueryDestination
A classification returned by the SP: 1 = visible to the supplier now, 2 = held / waiting, 3 = processed / the generic external value, 5 collapses to 3, 8 (export-mark) and 9 (high-risk supplier) are shown to callers as 3.
Early guardrail
A missing or invalid sender / receiver id is rejected before any DB round-trip, returning queryid = -2 as HTTP 200.

Screening

BAN API
An external content-moderation service that screens the requirement text for spam / abusive keywords.
Templated description
An auto-filled generic requirement (e.g. “I am interested in…”). Matched against 14 fixed patterns; such text skips the BAN API entirely.
Waiting state
A banned-keyword hit forces InForceDestination = 2 and reason -999; the enquiry is still saved but not shown to the supplier until resolved.

Fan-out & recovery

ENQ_DATA
One bundled RabbitMQ message published per saved enquiry; a downstream consumer splits it into FENQ, Lead-Management and Personalization sub-messages.
Lead Management (LMS)
The system that tracks each enquiry as a lead; fed via a 5-way sharded queue and mirrored to Kafka topic ENQ_PNS_DATA.
Personalization
The recommendation engine; its sub-message ends up on a Redis resque-style work queue.
Preferred-channel worker
Decides how the enquiry reaches the supplier — email, WhatsApp or app.
Backup & replay
On a save or fan-out failure the full request is written to a JSON file; the QueryParse cron re-POSTs it to this endpoint the next day.
GLID
GlobalID — the unique internal identifier for a buyer or supplier.
