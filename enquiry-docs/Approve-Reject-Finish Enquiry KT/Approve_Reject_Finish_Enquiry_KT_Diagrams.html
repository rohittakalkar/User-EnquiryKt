Approve / Reject / Finish Enquiry

Three endpoints act on an already-saved enquiry. Approve moves a waiting enquiry into the live supplier-facing table; Reject moves it into the bounced table with a reason; Finish triggers the actual communication (Lead-Management update plus an email / SMS data packet) for an already-live enquiry, once. Most approve / reject decisions are made automatically by a background “FENQ bot” that re-screens the text a few seconds after the enquiry lands in the waiting state; a human reviewer is the exception.

Enquiry Lifecycle

Approve / Reject / Finish Enquiry

POST /enquiry/approveEnquiry forces ApprovalReason = "6", updates DIR_QUERY_WAITING, then calls SP_PUSH_ENQ_TO_DIR_QUERY_V3 to move the row into a DIR_QUERY_<NN> shard; a duplicate-key error self-redirects to Reject with reason -94. POST /enquiry/rejectEnquiry remaps a small set of reason ids to 80–86, updates the waiting row only where FK_APPROVAL_REASON_ID IS NULL, then calls sp_push_enq_to_dir_bounced_new_v2. POST /enquiry/finishEnquiry requires query_destination = 1, reads the sharded row where DIR_QUERY_MAIL_SEND IS NULL, pushes LMS + comm queues, then stamps DIR_QUERY_MAIL_SEND = -7 (or -9 for SMS-only).

Business flowchart

Moving a saved enquiry to its outcome

Three transitions, mostly automated:

  • Approve — a waiting enquiry is accepted; its approval reason is always recorded as 6, and the row moves to the live table. An already-resolved query returns “Query Not Found” as a normal success.
  • Reject — a waiting enquiry is bounced with a reason; an enquiry that has already been approved cannot be rejected.
  • Finish — for a live enquiry only, builds and sends the communication once; a repeat call finds the idempotency flag set and does nothing.
  • FENQ bot (employee id 17967) — waits ~10 seconds, then re-screens the description and product name; either flagged → it calls Reject, both clean → it calls Approve; a later scoring step may trigger a second Reject with a computed reason.
  • Approve / Reject notify Lead Management only; the buyer / supplier email or SMS is triggered solely by Finish.

Data-flow diagram · Level 1

Where a waiting enquiry is resolved and communication is triggered

One waiting table, two stored-procedure moves, one comm trigger:

  • 1.0 Approve updates D1 and calls the move-to-live SP.
  • 2.0 Reject updates D1 (guarded) and calls the move-to-bounced SP, writing D3.
  • 3.0 Finish reads the sharded live row D2, pushes LMS + comm queues, and stamps the idempotency flag.
  • 4.0 FENQ bot consumes the waiting-enquiry queue and calls Approve / Reject over HTTP.

Sequence diagram · Flows C + E

The FENQ bot resolving a waiting enquiry, and a Finish call

The dominant automated path, plus a Finish:

  1. A new enquiry lands in the waiting state; the FENQ bot waits ~10 seconds and re-screens the description and product name.
  2. alt — either is flagged: the bot calls Reject (reason 13); both clean: the bot calls Approve, which moves the row to the live shard.
  3. A scoring step may then call Reject again with a computed reason.
  4. Separately, Finish is called for a live enquiry: if its mail-send flag is still null it pushes the LMS and communication queues and stamps the flag; otherwise it is a no-op.

Glossary

Business terms used above.

The three actions

Approve
Accepts a waiting enquiry and moves it into the live, supplier-facing table. The approval reason is always recorded as 6 regardless of what was sent.
Reject
Bounces a waiting enquiry into DIR_QUERY_BOUNCED with a reason. An already-approved enquiry cannot be rejected (guarded by FK_APPROVAL_REASON_ID IS NULL).
Finish
For an already-live enquiry, triggers the actual communication — a Lead-Management update and (unless SMS-only) an email / SMS data packet.
“Query Not Found”
Returned when the enquiry is no longer in the waiting table — already resolved, or never waiting. A normal success, not an error.

Automation

FENQ bot
A background consumer that auto-resolves most waiting enquiries. It runs as employee id 17967, so its actions look like a specific reviewer's in audit data.
10-second settle
The bot waits about ten seconds before re-screening, to let the enquiry's DB writes settle.
Re-screen
The bot checks both the description and the product name against an abuse-detection API; either one flagged rejects the whole enquiry.
Scoring step
A follow-up quality / duplicate check that can trigger a second Reject with a system-computed reason id.

State & idempotency

DIR_QUERY_WAITING
The review-pending table both Approve and Reject read and update before moving the row elsewhere.
DIR_QUERY_<NN> shards
The live enquiry tables, sharded by the receiver GLID's last two digits.
Move stored procedures
SP_PUSH_ENQ_TO_DIR_QUERY_V3 (approve) and sp_push_enq_to_dir_bounced_new_v2 (reject) perform the actual row moves; their internals are not visible from the API code.
DIR_QUERY_MAIL_SEND
Finish's idempotency flag. Set to -7 normally or -9 for SMS-only; once set, no future Finish call for that query does anything.
Reason -94
The system reason used when an Approve hits a duplicate-key conflict and self-redirects the enquiry to the bounced table.
