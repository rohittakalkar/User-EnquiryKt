Enquiry Attachment

Enquiry Attachment records the images and documents a buyer attaches to an enquiry, linked to its Query ID. There are two structurally different write paths into the same DIR_QUERY_ATTACHMENT table: a synchronous write API that trusts the client's paths and does nothing else, and a separate queue consumer that runs image moderation, fetches a permanent storage URL, and conditionally feeds Lead-Management enrichment. A third path reads the stored attachments back when a waiting enquiry becomes a purchased lead and forwards them to the Buy-Leads system.

Enquiry Attachment

Write path A: POST /enquiry/enquiryAttachment (before middleware.Validation). Needs a numeric Query ID, a non-empty ModID, at least one image or document, and an attach_type_id on every one; a single multi-row INSERT follows, with no status column, no queue, no Kafka. Write path B: the ENQUIRY_ATTACHMENT_WORKER consumer (its publisher was not found in the repos) inserts a narrower row with DIR_QRY_ATTACHEMENT_STATUS, moderating only the first original image and applying its verdict to all; approved images get a permanent URL, and if DIR_QUERY_MAIL_SEND is set and an attachment is approved it publishes Kafka topic LMS_LEADS_ENRICHMENT. Flow C: the FENQ bot reads dir_query_attachment (no status filter) and POSTs it to the Buy-Leads saveblattach API.

Business flowchart

Images and documents on an enquiry

Two independent write paths plus a forwarding read:

  • Flow A — direct save: the buyer's app uploads image / document paths with the enquiry's Query ID; after basic validation the rows are written straight to the DB and the buyer gets an immediate success. No moderation, no notification.
  • Flow B — moderation & enrichment: a separate queued message re-inserts the attachment with a moderation status. Only images are screened (documents are auto-approved); an approved image gets a permanent URL, and if the enquiry is flagged for mail an approved attachment is pushed to Lead-Management enrichment.
  • Flow C — lead transfer: when the FENQ bot turns a waiting enquiry into a purchased Business Lead, it re-reads every stored attachment for that enquiry — regardless of which path wrote it or its status — and forwards it to the Buy-Leads system.

Where an attachment is saved, moderated and forwarded

One table, two writers, one forwarder:

  • 1.0 Direct save validates and multi-row-inserts D1 (no status, no queue).
  • 2.0 Moderation consumer inserts D1 with a status, calls the moderation and permanent-URL services, reads D2, and conditionally publishes Kafka enrichment.
  • 3.0 Lead transfer reads D1 unfiltered and POSTs it to the external Buy-Leads API.

Sequence diagram · Flows A + B

A direct attachment save, and the separate moderation pipeline

A direct save and the separate moderation pipeline:

  1. The buyer's app posts image / document paths with the Query ID; the API checks the Query ID, ModID, that at least one attachment is present, and that each has a type id.
  2. alt — valid: one multi-row insert writes the rows and returns success; invalid: rejected (as HTTP 200 with an error body).
  3. Separately, a queued message reaches the moderation consumer, which re-inserts with a status.
  4. alt — first image approved: a permanent URL is fetched and, if the enquiry is mail-flagged, Kafka enrichment is published; rejected: no URL, no enrichment.

Two independent, non-identical INSERT paths write the same table — the write API sets no status column and runs no moderation, so an attachment it inserts can be forwarded to Buy-Leads without ever being screened. The queue's publisher was not found in either repo, only images are moderated (not documents), and fetchISQ() is a parked stub — all flagged in the source doc.

Glossary

Business terms used above.

The record

Enquiry attachment
An image or document a buyer attaches to an enquiry, always linked to its Query ID — there is no standalone attachment.
DIR_QUERY_ATTACHMENT
The single table both write paths insert into. Images are stored in up to four size variants (original / small / medium / large) with width and height columns.
attach_type_id
A numeric category code required on every image and document. Its meaning is not defined anywhere in code.
Two write paths
Path A (the synchronous write API) trusts the client's paths and stores no status; path B (a queue consumer) stores a moderation status but only original-size images.

Moderation

Image review
A “Leap Buyer Photos Review” API screens images. A response of “approve” sets status 1; anything else (including errors) sets status 2 (rejected).
First-image-only
Only the first original image in a message is sent for review; its verdict is applied to every image in that message.
Documents auto-approved
Documents are never screened — they always get the approved status.
Permanent URL
For an approved image, a permanent-storage service is called to replace the temporary path with a stable URL.

Downstream

DIR_QUERY_MAIL_SEND
A per-enquiry flag; only if it is set (non-null, non-zero) and an attachment is approved does the consumer publish enrichment.
Kafka LMS_LEADS_ENRICHMENT
The topic the moderation consumer publishes approved-attachment enrichment to — a different topic from the ENQ_PNS_DATA used by Save Enquiry / Call Enquiry.
Buy-Leads transfer
When the FENQ bot turns a waiting enquiry into a purchased Business Lead, it re-reads all stored attachments (no status filter) and POSTs them to the Buy-Leads saveblattach API.
Query ID
The enquiry identifier every attachment row links back to, produced by Save Enquiry.
