Knowledge Transfer · Engineering

Verification Process

A structured, primary + secondary cross-linked verification-event recorder. POST /user/userverificationdetails (WEBERP / SOA-WAPI only) validates a primary attribute plus optional related secondary attributes against 18 predefined categories, then writes each pair through a trustpg stored function. It is also the HTTP-loopback target of the USER_VERIFICATION_TRUSTPG queue, so a GST verification automatically produces a trust record here. It publishes nothing itself and has no read side of its own.

Trust & Compliance

Verification Process

Two entry points: direct (WEBERP / SOA-WAPI) and indirect (the trust-PG consumer looping back with a hard-coded key, fired by GST or bulk verification). Validation is strict JSON typing plus the 18-category map. When secondary attributes are present, no standalone primary record is written — one combined row per secondary.

Business flowchart

Recording a cross-linked verification event

The direct flow:

  1. Only WEBERP and SOA-WAPI pass the gateway; every field is strictly type-checked and datetime must match yyyyMMddHHmmss.
  2. The primary attribute id and every secondary key must be in the 18-category map — one invalid key rejects the whole batch.
  3. If the primary value is empty, nothing is written but the call still returns SUCCESS — a real gotcha.
  4. With secondary attributes present, one combined primary + secondary row is written per non-empty secondary (empty ones are silently skipped); otherwise a single primary-only row.
  5. Each row is a fn_insert_glusr_attribute_verification call on trustpg with its own 1-second timeout.

The indirect flow: GST or bulk verification publishes to USER_VERIFICATION_TRUSTPG; the consumer fills a missing mobile / email from glusr_usr, resolves the source category, and loops back into this same endpoint.

Where the primary + secondary event is written

One opaque store, reached two ways:

  • 1.0 Validate checks the gateway, strict types, and the 18-category map for the primary and every secondary key.
  • 2.0 Build pairs turns the request into one primary + secondary pair per non-empty secondary.
  • 3.0 Write each pair calls the trustpg stored function once per pair.
  • 4.0 Trust-PG consumer fills missing mobile / email from D2, resolves the source in D3, and loops back into 1.0.

Sequence diagram · Flow B

A GST verification producing a trust record

A GST verification producing a trust record via the queue:

  1. A GST consumer publishes to USER_VERIFICATION_TRUSTPG.
  2. alt — if the mobile / email value is empty, the consumer reads it from glusr_usr.
  3. The consumer resolves the source category, then loops back into POST /user/userverificationdetails with a hard-coded key.
  4. The write API validates (two callers, the 18-category map) and calls the trustpg stored function once per attribute pair.
  5. alt — a returned status other than 1 makes the consumer Nack for retry; otherwise it acks.

Glossary

Business terms used above.

The event model

Primary attribute
The attribute being verified in this event — e.g. a mobile number.
Secondary attributes
Related attributes recorded with the primary (e.g. the email or GST it was verified alongside) for cross-referencing and fraud-pattern detection.
18 predefined categories
Mobile, email, GST, PAN, CIN, TAN, company name, bank account, Aadhar, address, city, state, name, IEC, CEO name, zip, Udyam, lat-long. Adding one needs a code deploy.
One row per secondary
When secondary attributes are present, no standalone primary row is written — instead one combined primary + secondary row per non-empty secondary.
Empty primary = silent no-op
If the primary value is empty, nothing is written at all, yet the call returns SUCCESS.
fn_insert_glusr_attribute_verification
The trustpg stored function every write goes through; its table structure is opaque to the application.

Two entry points

Direct
WEBERP or SOA-WAPI call the endpoint over HTTP with a validation key.
Indirect
The USER_VERIFICATION_TRUSTPG queue's consumer loops back into the same endpoint with a hard-coded key, acting as a synthetic WEBERP caller.
Triggered by GST / bulk verification
When a GST or bulk verification completes, its consumer publishes to that queue, so a trust record is created here automatically.
Mobile / email auto-fill
If the loopback message omits the mobile / email value, the consumer reads the current value from glusr_usr before calling.

Relationship to Trust Verification

Distinct write path
A genuinely separate endpoint with its own validation and stored function, not the same as POST /user/verification.
Its own attribute-ID numbering
GST is 2721 here versus 2106 in the main verification system — do not conflate the two ID spaces.
Shared reads
The getverificationdetails / verifieddetail read endpoints are shared with Trust Verification and documented there.
GLID
GlobalID — the unique internal identifier for the supplier.
