WhatsApp Message Integration

This KT covers two genuinely independent features that only share a name. First, a WhatsApp Business integration record: a supplier's linked WhatsApp Business account, with Meta-side verification, KYC and quality-rating status, written only by internal admin / LMS tools and tracked as an ongoing relationship. Second, an outbound “app install” nudge: a generic notification endpoint that sends a WhatsApp (or SMS) message asking a user to install the IndiaMART app, gated by a strict 24-hour per-number frequency cap. Different tables, different databases, different purpose.

WhatsApp Message Integration

Integration record: POST serviceName MSG_PLATFORM_INTEGRATION (gateways GLADMIN / LMS), action i / u against Glusr_msg_platform_integration (meshpg). Status transitions into / out of the active bucket (sub-status 12–14 vs 15–19) write glusr_msg_platform_log; scam / spam flags write it independently. Nudge: the generic sendmsg endpoint, where source = WHATSAPP_8181 / WHATSAPP_9696 selects the WhatsApp branch; checkWhatsAppFrequency enforces a 24-hour cap against iil_whatsapp_msg_events (notification_pg_master) before an external vendor HTTP call.

Business flowchart

Two unrelated things that share the word “WhatsApp”

Read the two halves separately:

  • Integration record (Flow A / B) — an internal admin or LMS caller links or updates a supplier's WhatsApp Business account. Insert is an upsert; update is a partial, field-by-field change after an exact-id existence check. A status-change log row is written only when the sub-status actually moves into the active bucket (REINSTATED / UNLOCKED / REONBOARDED) or out of it (LOCKED … DELETED) — a first-time LIVE does not log. Scam / spam flagging is a separate, independent log write.
  • Outbound nudge (Flow C) — an internal trigger calls the generic sendmsg endpoint. Only two source values route to WhatsApp; everything else is SMS. Before sending: skip if the user is already on an app-installed device, skip if the SMS-side frequency table says so, then the WhatsApp 24-hour cap (only successful past sends count). If clear, an external vendor sends a template or free-text message.

Data-flow diagram · Level 1

Where the integration record and the outbound nudge live

Two tables in two databases, plus an external vendor:

  • 1.0 Integration write upserts / partially updates D1 and conditionally writes the log D2.
  • 2.0 Integration read returns D1 with every numeric status decoded via one-hot enum maps.
  • 3.0 Nudge gate checks the app-installed table and the SMS frequency table D4.
  • 4.0 WhatsApp frequency check counts non-failed rows in D3 (a different physical DB) within 24 hours.
  • 5.0 Vendor send is an external HTTP POST; nothing in these repos writes D3 back.

Sequence diagram · Flows A + C

Updating the integration record, and sending an app-install nudge

An integration update, then an app-install nudge:

  1. An admin / LMS caller sends action=u; the API checks the gateway, confirms the exact record id exists, and applies a partial update.
  2. alt — if the sub-status actually changed into or out of the active bucket, a status log row is written; if a scam / spam flag is present, a second, independent log row is written.
  3. Separately, an internal trigger calls sendmsg with source=WHATSAPP_9696.
  4. The gate skips already-installed users and SMS-throttled numbers; then alt — if the 24-hour WhatsApp cap is clear, an external vendor sends the message; otherwise it is silently skipped.

Glossary

Business terms used above.

Integration record

WhatsApp Business integration
A supplier's official WhatsApp Business account linked to IndiaMART through an external BSP vendor — an ongoing, status-tracked relationship, not a one-time setup.
BSP
Business Solution Provider — the external WhatsApp-messaging vendor (AiSensy / Meta / ValueFirst) the integration runs on.
Admin / LMS only
The integration record is written only by internal GLADMIN or LMS tools; the supplier never calls this API directly.
Sub-status buckets
Numeric statuses group into ACTIVE (11–14), PARTIALLY_ACTIVE (15), INACTIVE (16–19) and others. Moving into the active bucket (12–14) or out of it (15–19) is what triggers a log row.
First-time LIVE does not log
Status 11 (first activation) is deliberately excluded from the status-change log; only transitions through reinstated / locked / deleted states are recorded.
Scam / Spam flag
A Meta-side flag recorded as its own independent audit row (internal code 3 = SCAM, 4 = SPAM), separate from status-change logging.
One-hot response
The read API returns every possible enum key with a 1 / 0 value rather than a single string; clients scan for the key set to 1.

Outbound nudge

App-install nudge
A transactional WhatsApp (or SMS) message asking a user to install the IndiaMART app.
Shared dispatch point
The generic sendmsg endpoint sends both SMS and WhatsApp; the channel is chosen purely by the caller's source value. Only WHATSAPP_8181 and WHATSAPP_9696 route to WhatsApp.
24-hour frequency cap
Per mobile number, the same nudge is not re-sent within 24 hours. Only successful past attempts count, so a failed attempt can be retried sooner.
iil_whatsapp_msg_events
The send-history table the cap is checked against — in a different physical database (notification_pg_master) from the integration record.
Already-installed skip
If the system already knows the user is on an app-installed device, the nudge is skipped entirely.
Template vs free-text
WHATSAPP_9696 sends a pre-approved content template; other WhatsApp sources send a hardcoded free-text message.

Boundaries

Not the social-contact toggle
A supplier's public “show WhatsApp as a contact method” flag (IS_WHATSAPP_ACTIVE) is a third, separate feature covered by the Social Contacts KT.
Generic fan-out
The integration write publishes to a shared comp.sync.* company-sync channel used by many domains; no consumer dedicated to this feature was found.
GLID
GlobalID — the unique internal identifier for the supplier.
