Knowledge Transfer · Engineering

Buyer-Supplier Matchmaking

A system-created “proof of connection” record, written whenever a buyer genuinely contacts a supplier. Two independent entry points feed it: the platform's internal LEADS system (a sync write plus a Kafka mirror write) and the Lead-Management System (a separate RabbitMQ queue). Its main use is as a ratings anti-fraud gate — no matchmaking record and the rating is auto-disabled. The record is permanent; there is no “un-match”.

Buyer–Seller Discovery

Buyer-Supplier Matchmaking

POST /user/bsmatchmaking (gateway LEADS only) synchronously calls sp_insert_contacts with glid1 = supplier, glid2 = buyer, then publishes a Kafka event whose consumer does a second write to the same physical database. An LMS RabbitMQ consumer writes the same table independently. The ratings anti-fraud consumer runs a COUNT and, on a miss, disables the rating (display status -1, reviewer -999).

Business flowchart

A system-made proof that two users connected

Four flows, all system-driven:

  • Flow A — internal system: a contact event makes the LEADS system call the API; after the mandatory + LEADS-gateway check it runs sp_insert_contacts synchronously, then publishes a Kafka event. The consumer re-validates; for source 3/4 it only logs, otherwise it re-derives the dual-side flag and does a duplicate write to the same DB.
  • Flow B — LMS: the Lead-Management System publishes to its own queue; the consumer strict-type-checks the message (invalid → ack and drop, no retry), does an unconditional dual-side flip, and writes the same table.
  • Flow C — anti-fraud: a rating event triggers a COUNT of matchmaking records for the pair (source_id in -1, 1, 3, 4); found → no action, missing → the rating is disabled via the rating write API.
  • Flow D — read: when a supplier opens a buyer's profile, one query returns connected? and blocked? together.

Where the connection record is written and consulted

One canonical table, several writers and one key consumer:

  • 1.0 Sync write validates and calls sp_insert_contacts on D1, then publishes to Kafka.
  • 2.0 Kafka mirror consumer re-validates and does a second write to D1 (same physical DB).
  • 3.0 LMS consumer writes D1 from an independent RabbitMQ queue.
  • 4.0 Rating anti-fraud consumer counts D1 and, on a miss, disables the rating in D2 via the rating write API.
  • 5.0 Buyer-profile read joins D1 with the blocked-status table.

Sequence diagram · Flows A + C

Creating a record, then the ratings anti-fraud check

A record being created, and later checked by the ratings pipeline:

  1. The LEADS system calls the API; it validates the mandatory fields and the LEADS gateway, then calls sp_insert_contacts (supplier, buyer) synchronously and publishes a Kafka event.
  2. alt — the Kafka consumer logs only for source 3/4; otherwise it does a duplicate sp_insert_contacts to the same DB.
  3. Later, a rating event makes the anti-fraud consumer COUNT matchmaking records for the pair.
  4. alt — count > 0: no action. Count 0: it calls the rating write API to disable the rating (display -1, reviewer -999).

Glossary

Business terms used above.

The record

Proof of connection
A row written by the system — not by a buyer or supplier — whenever a real contact event (enquiry, order, conversation) happens.
glid1 = supplier, glid2 = buyer
The fixed column order, consistent across the write, the read and the anti-fraud consumer.
Permanent
Once written, a matchmaking record is never removed; there is no “un-match” concept (unlike Blocking).
Duplicate write by design
The sync write and its Kafka-driven consumer both insert the same row into the same physical DB; investigating an event normally shows two writes.
Dual-side flag
A field indicating whether the connection is registered from one side or both. Three code paths (sync write, Kafka consumer, LMS consumer) each derive it differently.

Two entry points

Internal “LEADS” system
Calls the sync write API when a contact event fires; the API also publishes a Kafka event for the mirror write.
Lead-Management System
Publishes buyer-supplier contact events to its own RabbitMQ queue, independent of platform activity. Malformed messages are acked and dropped without retry.
source_id
Identifies where a record came from; the anti-fraud check only counts sources in {-1, 1, 3, 4}. Sources 3 / 4 are assumed already written by another path, so the Kafka consumer only logs them.

Downstream

Ratings anti-fraud gate
When a rating is processed, this record is counted for the buyer-supplier pair; a missing record disables the rating (display status -1, reviewer -999) with no human involved.
Buyer-profile read
A supplier viewing a buyer sees connected? and blocked? returned together from one joined query.
GLID
GlobalID — the unique internal identifier for the buyer or supplier.
