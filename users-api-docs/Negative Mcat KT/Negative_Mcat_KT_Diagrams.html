Knowledge Transfer · Engineering

Negative Mcat

An internal category-exclusion switch — mark a micro-category (Mcat) as “not applicable” for a whole supplier account or one product listing, without deleting the product. Insert / soft-delete only, 26 internal gateways allowed. Every change fans out three ways: a search replica, an alert / blacklist DB (which tracks only supplier + mcat, losing item granularity), and a forward-only relay into an external “ETO rejection” queue. No supplier notification, no cron.

Catalog & Categorisation

Negative Mcat

POST /negative/mcat takes action_flag I or D. Insert writes NEGATIVE_MCAT_FOR_PRODUCTS with IS_DELETED=0; delete is a soft UPDATE (IS_DELETED=1) matched on the (supplier, item, mcat) triple. On success it publishes to USER_NEGATIVE_MCAT; three consumers replicate or forward. The read returns only active rows with the mcat name; a comma-separated multi-item lookup silently returns nothing.

A surgical category-exclusion switch

Two write actions and a read:

  • Insert (action_flag=I) — after the gateway check (26 callers) and mandatory fields, item_id defaults to -1 (account-wide); an employee id is resolved to a name; a row is inserted with IS_DELETED=0.
  • Delete (action_flag=D) — a soft UPDATE setting IS_DELETED=1, matched on the (supplier, item, mcat) triple, not the primary key. The row is retained.
  • Both publish USER_NEGATIVE_MCAT on success, fanning out to a search replica, an alert / blacklist DB (supplier + mcat only — item granularity collapses), and a forward-only relay to an external ETO queue.
  • Read — returns only active (IS_DELETED=0) rows with the mcat name; a comma-separated item_id list returns an empty result with no error.

Where an mcat exclusion is written and fanned out

One primary write, a three-way fan-out:

  • 1.0 Validate & write inserts / soft-deletes D1 and publishes on success.
  • 2.0 Search-replica consumer mirrors the change into D2.

Marking a negative mcat and its three-way fan-out

An insert and its three-way fan-out:

  1. The API checks the 26-caller gateway and mandatory fields.
  2. alt — if an employee id is present, it is resolved to a name; otherwise “User” is used.
  3. A row is inserted with IS_DELETED=0 and USER_NEGATIVE_MCAT is published.
  4. par — three consumers run: the search-replica writes searchPg; the alert consumer upserts alertPg keyed by supplier + mcat; the relay consumer forwards the event to the external ETO queue.

Glossary

Business terms used above.

The exclusion

Mcat
Micro-category — IndiaMART's product-classification unit. Every listing sits under one or more mcats.
Negative mcat
An explicit mark that a given mcat is not applicable for a supplier or product — a surgical alternative to deleting the listing.
Supplier-level vs item-level
item_id is optional; absent, it defaults to -1 meaning the exclusion applies to the whole account.
action_flag I / D
Insert an exclusion or soft-delete one. Any other value is rejected.
Soft-delete
Delete is an UPDATE setting IS_DELETED=1, matched on the (supplier, item, mcat) triple rather than the primary key. The row is kept for audit.

The fan-out

USER_NEGATIVE_MCAT
The queue every successful insert / delete publishes to.
Search replica
A consumer that mirrors the change into a search / directory-facing copy of the table so listing exclusions show in search results.
Alert / blacklist DB
A consumer that upserts NEGATIVE_MCAT_FOR_PRODUCTS_CURRENT keyed only by supplier + mcat — item-level granularity is lost in this copy.
Forward-only relay
A consumer with no local DB write; it re-publishes the event into ETO_REJECTION_MASTER_QUEUE, whose downstream sits outside the three repos.

Access & reads

26 internal gateways
A wide allowlist — GLADMIN, Weberp, Tollfree, PCAT-Admin, Tolexo, IMOB, Email Marketing and many more — making this a broadly-touched internal feature.
Employee-name resolution
If an employee id is supplied it is resolved to “Name (id)”; otherwise the record is attributed to “User”.
Active-only read
The read returns only IS_DELETED=0 rows, with the mcat name joined in.
Broken multi-item read
A comma-separated item_id list silently returns an empty result — the code branch exists but the query is never built.
No notification, no cron
Purely internal; the supplier is never told, and no scheduled job touches this feature.
GLID
GlobalID — the unique internal identifier for the supplier.
