Bank Details

A supplier can save several bank accounts (account number, IFSC, holder name); exactly one is the prime account used for payouts and lending. Every change runs through external verification (PennyDrop), a banned-content check on the free-text fields, and a trust-database sync. It is a Type=BankDetails branch of the shared user-details write endpoint — the most heavily fanned-out feature in this series.

Bank Details

Six flows: supplier adds an account (Flow A), a system / ERP adds one (Flow B), supplier updates or re-primes an account (Flow C), soft delete (Flow D), banned-content auto-clean (Flow E), and read (Flow F). Who is calling — classified as USER, SYSTEM or MERP — decides prime assignment.

Business flowchart

Who can add an account, and how “prime” is decided

The branch first classifies the caller, which decides whether the new account becomes prime:

  • USER (supplier apps, GLADMIN, BUYERMY, SELLERMY) — always prime, no query.
  • SYSTEM (ERP, WEBERP, PayWim, and any unmatched gate) — prime only if a 100 ms pre-check finds no existing verified prime account; the check fails open to prime on timeout.
  • MERP — never auto-prime.

Setting a new prime un-primes every other account. Delete is soft (ENABLED = -1) and does not clear the prime flag. Mail / SMS goes out only for supplier-driven changes where account number, IFSC or prime status actually changed.

Data-flow diagram · Level 1

Where bank-account data moves across processes and stores

One synchronous write, then a four-way fan-out:

  • 1.0 Validate & classify checks the gateway allowlist and derives reqType; for SYSTEM it reads D3 to decide prime.
  • 2.0 Write account inserts / updates D1; 3.0 Un-prime others runs async when a prime is set.
  • 4.0 General sync + notify reads GLUSR_USR for the mail / SMS; 5.0 Verify forwards the account to PennyDrop.
  • 6.0 Trust sync replicates into D2; 7.0 Banned detect screens the free-text fields and calls the write API back to blank anything flagged.

Sequence diagram · Flow A / C

Adding or updating a bank account

Add (id=="") and update (id!="") share one path:

  1. The API checks the gateway allowlist and classifies the caller as USER / SYSTEM / MERP.
  2. alt — for SYSTEM, a 100 ms pre-check decides prime; a timeout is treated as “no existing prime”.
  3. The row is inserted or updated; if a prime was set, an async query un-primes the rest.
  4. Four messages are published. Consumers run in par: general sync + mail / SMS, PennyDrop verify, trust-PG sync, banned-content detect.
  5. alt in the notifier — skip mail / SMS if nothing material changed, or if a prime account has a blank holder name.

Glossary

Business terms used above.

Accounts & the prime rule

Prime account
The one bank account per supplier used as the default for payouts and lending integrations. Setting a new prime un-primes the previous one.
reqType — USER
Caller is a supplier-facing gate (supplier app, GLADMIN, BUYERMY, SELLERMY). A new account is always made prime.
reqType — SYSTEM
Caller is an automated system (ERP, WEBERP, PayWim, or any gate not otherwise matched). A new account becomes prime only if no existing verified prime account is found.
reqType — MERP
Caller is the MERP internal tool. A new account is never auto-primed; prime must be set explicitly.
Un-prime
An async query that clears GLUSR_BANK_ISPRIME on every other account for the supplier, keeping the “only one prime” rule — enforced in code, not by a DB constraint.
Soft delete
Delete sets ENABLED = -1; the row and its history stay. It does not clear the prime flag, so a disabled account can still read as prime (known gap).

Verification & safety

PennyDrop
The external partner that confirms a bank account number + IFSC are real by making a tiny test deposit.
Banned-content detection
A shared check that screens the bank name, address and holder-name free-text fields for abusive / spam content and auto-blanks anything flagged.
VALIDATION_KEY
A shared secret the banned-content consumer uses to call the write API back and save the cleaned fields.
Trust-domain sync
A dedicated consumer that replicates bank-detail changes into the Trust database (trustPg), feeding TrustSeal-style eligibility.
KYC status
A per-account status column on the bank record; not driven by this flow directly.

People & systems

Supplier
The IndiaMART seller who owns the bank accounts.
GLID
GlobalID — the unique internal identifier for one user / company account.
Gateway allowlist
The fixed set of callers permitted to write bank details: MAPI, GLADMIN, BUYERMY, SELLERMY, ERP_BT, ERP_NACH, WEBERP, PAYWIM, MERP, ANDWEB.
Consumer
A background worker that processes one queue asynchronously. Bank Details has four: general sync, verify, trust sync, banned detect.
Fan-out
Publishing the same change to several queues at once so independent downstream jobs each get it.
