Payment Transaction — International

This feature records international buyer-to-seller payments — buyer and seller ids, buyer country and name, currency, amount and a linked invoice. It is insert-once: the full record is written on action=i, and the only thing a later action=u can change is a free-form custom-details JSON blob. Core financial fields are immutable through the API. There is no read endpoint, no queue, no cron — whatever consumes this data does so outside the reviewed code.

Payment Transaction — International

POST /user/addpaymenttxndetails (gateways GLADMIN / SELLERMY / IMOB / ANDROID / IOS). action=i requires buyer id, seller id, buyer ISO, buyer name, currency id, amount and invoice URL; the invoice id is derived as the text after the first # in that URL; a 12-column INSERT into Glusr_international_txn_detail (meshpg) follows, with no RETURNING. action=u needs only id and seller id and updates only usr_txn_details, matched on (derived invoice id, seller id).

Business flowchart

A write-only log of cross-border payments

Two actions, deliberately asymmetric:

  • Insert — an internal app submits the whole transaction. All seven core fields are mandatory; the transaction date, if given, must match a strict format; any custom details must be a JSON object. The invoice id is pulled automatically from the invoice URL (the part after #).
  • Update — only the custom-details blob can change, matched by invoice id and seller id. Amount, buyer info and currency sent on an update are silently ignored — there is no API way to correct them afterwards.

No reference number is returned, so the caller must remember its own invoice URL / id to update later. No notifications are sent.

Data-flow diagram · Level 1

Where an international payment record is written

A single table, one write per action:

  • 1.0 Validate checks the gateway, the mandatory fields, the date format and the JSON shape.
  • 2.0 Insert derives the invoice id from the URL and writes all 12 columns to D1 (meshpg).
  • 3.0 Update changes only usr_txn_details on D1, matched on (invoice id, seller id).
  • No read, queue, consumer or cron is attached.

Sequence diagram · Flows A + B

Logging a transaction, then revising its custom details

An insert, then a details-only update:

  1. An internal app posts action=i with the full transaction; the API runs the gateway check, the mandatory-field and type checks, the date-format check and the JSON-object check.
  2. The invoice id is derived from the invoice URL and a 12-column row is inserted; no id is returned.
  3. Later the app posts action=u with the invoice id, seller id and a new custom-details object.
  4. alt — custom details present: only usr_txn_details is updated on the matched row. Absent: the query is left incomplete and the update effectively does nothing.

Glossary

Business terms used above.

The record

International payment transaction
A cross-border buyer-to-seller payment. The actual money movement happens outside IndiaMART; this feature only logs it.
Glusr_international_txn_detail
The single meshpg table holding one row per logged transaction.
Invoice id (derived)
Not submitted directly — taken as the text after the first # in the invoice URL. No # means an empty invoice id.
usr_txn_details
A free-form JSON blob of supplementary details — the only field an update can change.
Insert-once
The full record is written on action=i; core fields are immutable through the API thereafter.

The two actions

action=i
Insert. Requires buyer id, seller id, buyer ISO, buyer name, currency id, amount and invoice URL; writes all 12 columns.
action=u
Update. Requires only id and seller id; changes only usr_txn_details, matched on (invoice id, seller id).
Silently-ignored fields
Amount, buyer name and other core fields sent on an update are dropped without error — a wrong amount cannot be fixed via the API.
No reference number
The insert response returns no generated id; the caller must track its own invoice URL / id to update later.

Boundaries

No read endpoint
Nothing in the reviewed repos reads this table; a report or reconciliation tool would use direct DB access or a new API.
No side effects
No RabbitMQ, Kafka, Redis, cron or notification is attached — a pure synchronous write.
Strict date format
A supplied transaction-creation date must be exactly 14 characters and parse as YYYYMMDDHHMMSS, else the request is rejected.
GLID
GlobalID — the unique internal identifier for the buyer or seller.
