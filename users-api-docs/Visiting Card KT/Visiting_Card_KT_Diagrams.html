Knowledge Transfer · Engineering

Visiting Card

A photo of the supplier's physical business card (front / back), driven through a multi-team review: field capture → WebERP enrich → WebERP design → WebERP approve. A separate No Visiting Card status distinguishes “doesn't have one” from “not uploaded yet”. Pending events sync to a dedicated approval database carrying paid-status, work-order and enterprise context so reviewers can prioritise.

Trust & Compliance

Visiting Card

One write endpoint routes to insert, update or the NO_VC path. Any new photo or design update resets the enrich / design / approval flags, restarting the review. Only pending (non-terminal) writes publish the approval event; the consumer refreshes a latest-snapshot queue and appends an audit row in a separate database.

Business flowchart

A multi-team review behind one photo

The write branches by what is sent:

  • Insert (no card id) — needs at least one attachment or design update; creates the record and sets the companion “has visiting card” flag to Yes.
  • Update (card id present) — routes by TYPE: GLADMIN comment, WebERP ENRICH / DESIGN / APPROVE / ENRICHDESIGN, or a field-capture new photo / design update. A new photo or design update resets the enrich / design / approval flags.
  • No Visiting Card (TYPE=NO_VC) — upserts only the companion table to No; never touches the card table.
  • After any successful write, the companion flag is set to Yes — unless the card was rejected with a zero count, which flips it to No.
  • Only a pending / empty-status write publishes the approval event.

Data-flow diagram · Level 1

Where card data, the companion flag and the review queue live

The write touches meshpg; the approval consumer works a separate database:

  • 1.0 Validate & route decides insert / update / NO_VC.
  • 2.0 Write card updates D1; 3.0 syncs the companion flag in D2.
  • 4.0 Publish fires the approval event only for pending states.
  • 5.0 Approval consumer reads the priority context from D5, refreshes the pending-approval snapshot in D3 (delete + insert) and appends an audit row to D4.
  • 6.0 Read returns the companion status plus the latest card per approval state.

Sequence diagram · Flows A + F

Capturing a card and building the review queue

A field-capture insert, then the approval consumer:

  1. The write API validates the gateway and mandatory fields, inserts the card, and sets the companion flag to Yes.
  2. alt — status pending / empty: it publishes VISITING_CARD_SERVICE; a terminal status does not.
  3. The consumer reads customer-type, work-order count and enterprise type, and reads paid-status from a local JSON file.
  4. It replaces the pending-approval snapshot (delete + insert) and appends an audit row.
  5. alt — any step failing Nacks the message for retry; otherwise it acks.

Glossary

Business terms used above.

Card states

Pending (P) / empty
Card uploaded, decision not yet made. This is the state that enters the review queue.
Approved (Y)
Final approval given; the card becomes a public trust signal.
Rejected (R)
Card rejected — e.g. unclear photo or wrong details.
No Visiting Card
A companion status (N) meaning the supplier reported they have no card — distinct from “not uploaded yet”.
“Has visiting card”
The companion flag (Y) set by almost any successful card write; only a reject-with-zero-count flips it back to N.
Review-cycle reset
Uploading a new photo or design update nulls the enrich / design / approval flags, so the review restarts from scratch.

The review workflow

Field capture
The field team or supplier uploads the front / back photo (and location on a first capture).
WebERP ENRICH
An internal reviewer extracts and verifies the details on the card.
WebERP DESIGN
An internal reviewer approves the scan quality — readable, correct orientation.
WebERP APPROVE
The final decision: Approved or Rejected.
ENRICHDESIGN
A combined step doing enrich and design in one update.
GLADMIN comment
An internal admin annotation on the record; no separate ticketing system.

The approval queue

Approval database
A separate approvalPg instance the consumer writes — not the main meshpg.
Pending-approval snapshot
A table rebuilt per event (delete + insert) so it always holds the latest state per card, never history.
Audit trail
An append-only log of every visiting-card event the consumer processes.
Priority context
Paid-status, work-order count and enterprise type attached to each queue entry so reviewers can work paying / enterprise customers first.
Custtype JSON lookup
Paid-status is read from a local JSON file keyed by customer-type, not from a database.
GLID
GlobalID — the unique internal identifier for the supplier.
