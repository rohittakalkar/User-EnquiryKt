Knowledge Transfer · Engineering

SellOnIM Log

SellOnIM Log tracks a new supplier's onboarding journey — name given, company given, email given, products added, address, GST, and a best-time-to-call. It is insert-or-update by LOG_ID. For one specific customer type, a successful journey update also fires a downstream pipeline: five sequential eligibility gates that, if all pass, place the supplier in the internal calling / verification queue. A failed gate is permanent — there is no automatic re-evaluation.

Onboarding & Lead Qualification

SellOnIM Log

POST /user/sellonimlog (serviceName USER_SELLONIM_LOG). The route is JWT-exempt; a Gateway_v1 allowlist is the only auth. BEST_TIME_TO_CALL (if present) must be RFC3339. A lookup merges FK_PARENT_GLUSR_ID / GLUSR_USR_APPROV from glusr_usr, then sellonim_log is inserted (RETURNING sellonim_log_id) or updated (WHERE sellonim_log_id = $n AND fk_glusr_usr_id = $m). On success and CUSTTYPE_ID == "39" a RabbitMQ message drives the USER_SELLONIM_CALLING consumer's five gates, ending in an iil_supp_verification insert.

Business flowchart

An onboarding-journey log that can qualify a call

A running log, plus a conditional qualification pipeline:

  • Flow A — journey log: each step's progress is recorded. No LOG_ID inserts a new row; a LOG_ID updates the matching row, but only if it belongs to the same supplier. Record id, supplier id and mobile act as lookup keys and cannot be changed on update.
  • Flow B — calling eligibility: only for one customer type, a successful update fires a downstream check of five gates — no disqualifying verification flag, priority score in the right band, no risky duplicate-email account, no duplicate GST, and not already queued in the last 30 days. All five must pass, in order; the first failure stops the chain.
  • All five pass → a new calling-queue entry is created with the best-time-to-call. A failure is silent and permanent — re-qualification needs a fresh journey update.

Data-flow diagram · Level 1

Where the journey is logged and the calling queue is fed

A two-round-trip write, then a gated consumer:

  • 1.0 Journey write reads glusr_usr for two derived columns, then inserts / updates D1 (approvalpg).
  • 2.0 Eligibility consumer runs five sequential SELECT gates against D2–D6 (meshpg).
  • 3.0 Queue insert writes D6 (iil_supp_verification) only if all gates pass.
  • No read endpoint, cron, Kafka or Redis is attached.

Sequence diagram · Flows A + B

Logging a journey step, then the 5-gate calling-eligibility pipeline

A journey update and the eligibility pipeline:

  1. An allowed app posts a journey step; the API checks the RFC3339 date and the gateway, merges two derived columns from glusr_usr, and inserts or updates sellonim_log.
  2. alt — success with CUSTTYPE_ID = 39: a message is published; otherwise nothing downstream happens.
  3. The consumer runs gates 1–5 in order, short-circuiting on the first failure or DB error.
  4. alt — all five pass: an iil_supp_verification row is inserted; any gate fails: the message is acked as “not eligible” with no retry.

Glossary

Business terms used above.

The journey log

SellOnIM
A new supplier's onboarding journey on IndiaMART — the steps from signup to a usable selling profile.
sellonim_log
One row per (supplier, LOG_ID) recording which onboarding steps are done and the best time to call.
Insert vs update
No LOG_ID inserts a new row; a LOG_ID updates — but only if it belongs to the same supplier, otherwise zero rows change and it is reported as a failure.
Locked keys
Record id, supplier id and mobile are lookup keys on update; values sent for them are ignored.
BEST_TIME_TO_CALL
An optional RFC3339 timestamp, reformatted server-side and carried through to the calling-queue entry.

The five gates

Trigger
The downstream pipeline runs only for CUSTTYPE_ID == "39"; every other customer type just updates the log.
Gate 1 — verification history
No prior disqualifying verification flag on the supplier.
Gate 2 — priority band
The supplier's FCP priority score is exactly 0.8 or 0.9.
Gate 3 — duplicate email
No other risky (paid or fcp-flagged) account shares this supplier's de-duplicated email.
Gate 4 — duplicate GST
No other supplier shares this supplier's GST number.
Gate 5 — recency
The supplier has not already been placed in the calling queue in the last 30 days.

Outcome

Calling / verification queue
iil_supp_verification — the table the internal calling team works from. A passing supplier is inserted here with fixed source / weight / priority constants.
Permanent “not eligible”
A failed gate acks the message as processed-but-not-qualified. There is no cron and no automatic retry; a fresh journey update is needed to re-evaluate.
Short-circuit chain
Gates run in order; the first failure or DB error stops the rest.
GLID
GlobalID — the unique internal identifier for the supplier.
