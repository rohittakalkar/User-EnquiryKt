Knowledge Transfer · Engineering

User Blacklist & Fraud Defense

“Blacklist” is really several independent fraud-defense mechanisms sharing a name: a human-curated manual blacklist (update-only), an automated ML fraud-suspect list (read-only), a DB-side fraud-check function keyed by GLID, a chat-derived signal that forwards matches to an internal service, and an inline domain-level check that silently drops catalog-view events for blacklisted, disabled or invalid users. No customer-facing notifications anywhere; no cron.

Trust & Compliance

User Blacklist & Fraud Defense

The mechanisms do not trigger each other. The manual blacklist API only updates existing rows — no INSERT path exists in the code. The ML list is written by a model outside this codebase. The domain-level check is consulted inline by the Business-Feed consumer and blocks on any of eight independent flags.

Business flowchart

Five independent mechanisms under one name

Each lane is self-contained:

  • Manual blacklist — an admin updates a value's status (block / unblock) or whitelists a whole GLID. If the value is not already in the table, the update returns “No Record Exist” — there is no INSERT.
  • ML fraud suspects — a model flags accounts automatically; callers read the status for up to 10 GLIDs at once; an admin can add a false-positive exception.
  • Chat signal — when a chat message contains a mobile / email that matches an active manual blacklist row, a summary is forwarded to the internal GLADMIN Blacklist Service. Nothing is written locally.
  • Domain-level check — on a catalog view, CheckUserBlocked computes eight flags in one query; any one true and the view event is dropped, never recorded.
  • Deprecated write API — always returns a canned “deprecated” body.

Data-flow diagram · Level 1

Where each blacklist signal is written and read

Five processes, each with its own store; nothing flows between them:

  • 1.0 Update manual value writes D1 (UPDATE only).
  • 2.0 Read value / GLID fraud-check reads D1, or calls the DB function D2 when only a GLID is given.
  • 3.0 Read ML suspects reads D3.
  • 4.0 Chat signal reads D1 and forwards a match to the external service.
  • 5.0 Domain-level check reads D4 (a composite of blacklist, user, employee and item tables) and drops the event on any block flag.

Sequence diagram · Flow D

The inline blacklist gate on a catalog view

The inline gate that runs before a catalog-view event is stored:

  1. The Business-Feed consumer receives a catalog-view event where viewer ≠ seller.
  2. It calls CheckUserBlocked, a single composite query (1 s timeout) joining the user row against the blacklist, employee and item tables.
  3. Eight flags are computed: disabled, blacklisted email / mobile / alt-mobile / email-domain, out-of-stock, invalid mobile, employee.
  4. alt — any flag true: the event is silently dropped. Otherwise it proceeds to a Redis meeting-log check and the normal insert.

A user with no record is treated as not blocked.

Glossary

Business terms used above.

The mechanisms

Manual blacklist
An admin-curated list of flagged attribute values (mobile, email, etc.). The API only updates existing rows — there is no INSERT path in the code.
ML fraud suspects
A list of accounts scored as suspicious by a machine-learning model that runs outside this codebase. Read-only from here.
fn_sp_suspected_fraud_detection
A database-side function called when GET /blacklistvalues is given only a GLID. Its body lives in the DB, not the repos; its relation to the ML list is unconfirmed.
Chat-derived signal
A consumer that checks mobiles / emails shared in chat against the active manual blacklist and forwards any match to the GLADMIN Blacklist Service. It writes nothing locally.
Domain-level real-time check
An inline check (CheckUserBlocked) the Business-Feed consumer runs before recording a catalog view; a blocked view is silently dropped.
Deprecated write API
POST /user/blacklist — still routed, but always returns a canned “This API is deprecated now” body.

States & flags

Blacklist status “1”
The only status value the checks act on — an actively-flagged value. Other statuses leave the row inert.
Whitelist-by-GLID override
A separate write path that marks every blacklist row tied to one GLID as trusted, instead of updating a single value.
Fraud-suspect probability
The model's confidence score that an account is suspicious, returned by GET /readmlfraud.
Fraud-suspect exception
A manual exemption for a specific account, to handle a false positive. Accounts can be excepted but not removed from the list.
IS_DOMAIN 0 / 1 / 2
On the domain-level check: 0 = email match, 1 = email-domain match (with indiamart.com hard-exempt), 2 = mobile match.
The eight block flags
disabled, blacklisted email / mobile / alt-mobile / email-domain, out-of-stock item, invalid mobile format, IndiaMART employee. Any one true blocks the view.

People & systems

GLADMIN / BI team
The internal team that curates manual blacklist values and whitelist overrides. The only writers to that API.
GLADMIN Blacklist Service
An internal downstream service that receives chat-match summaries. What it does with them is outside these repos.
Business-Feed consumer
The Kafka consumer for catalog-view events; it runs the domain-level blacklist gate inline before writing each view.
GLID
GlobalID — the unique internal identifier for one user / company account.
