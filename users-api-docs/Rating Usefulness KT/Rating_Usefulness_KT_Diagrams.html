Knowledge Transfer · Engineering

Rating Usefulness

A “was this rating helpful?” vote — helpful or abuse — by another buyer. One vote per buyer per rating. The vote is recorded, the rating's helpful / abuse counts recomputed, and written back onto the parent rating row via a loopback into the Supplier Rating write API, then replicated to an approval database. Zero counts are hidden. No cron, no supplier notification. It reuses the Supplier Rating controller internally.

Ratings & Reviews

Rating Usefulness

POST /rating_usefulness (its own gateway allowlist) inserts one GLUSR_RATING_USEFULNESS row; on a genuine new row it recomputes counts and publishes to a dedicated queue whose consumer HTTP-loops-back into /supplierrating with CALLEDFROM=RATING_USEFULNESS_WRITE, which updates GLUSR_RATING and fans out to the notification-PG consumer for approvalPg replication.

Business flowchart

A vote on a rating, written back onto the rating

One vote, four DB round-trips across two databases:

  1. The buyer votes helpful (1) or abuse (-1); the API checks the flag and its own gateway allowlist.
  2. A row is inserted into GLUSR_RATING_USEFULNESS. Any insert failure — not just a duplicate — is reclassified as “Record already exists” and reported as HTTP success.
  3. On a genuine new row, the helpful / abuse totals are recomputed and published to a dedicated queue.
  4. The consumer HTTP-loops-back into /supplierrating with a hard-coded key; that updates RATING_USEFULNESS_COUNT / RATING_ABUSE_COUNT on the rating and publishes again, landing in the notification-PG consumer which replicates the counts to approvalPg.

The counts surface inside GET /supplierrating; a zero count comes back as null, with a readable label like “3 users found this helpful”.

Sequence diagram · Flow A

A helpful / abuse vote, end to end

A helpful vote propagating to two databases:

  1. The API checks IS_HELPFUL is 1 or -1 and the gateway, then inserts the vote row.
  2. alt — insert failed: return “Record already exists” as success. Otherwise recompute the totals and publish USER_RATING_USEFULNESS.
  3. The consumer loops back into /supplierrating with CALLEDFROM=RATING_USEFULNESS_WRITE; the counts are written to GLUSR_RATING and SUPPLIER_RATING_NEW is published.
  4. The notification-PG consumer replicates the counts into approvalPg.

Glossary

Business terms used above.

The vote

Helpful (1) / abuse (-1)
The only two accepted values. There is no middle option.
One vote per buyer per rating
A second attempt returns “Record already exists” — reported to the caller as HTTP success so the UI shows no confusing error.
Any failure treated as duplicate
The code string-matches the insert error text; a transient DB error is also reported as “you already voted”, not as an error.
No self-vote block
Nothing stops the original rater from voting on their own rating — no comparison of the voter against the rating's buyer id exists.

Count write-back

Recompute on genuine new vote only
A duplicate vote never triggers any count recompute or downstream write.
HTTP loopback
The consumer does not write the rating row directly — it calls the Supplier Rating /supplierrating endpoint with CALLEDFROM=RATING_USEFULNESS_WRITE.
RATING_USEFULNESS_COUNT / RATING_ABUSE_COUNT
The physical columns on GLUSR_RATING that hold the totals. Input and output API field names differ from these.
approvalPg replica
A second consumer copies the new counts into a separate approval-workflow database.
Zero hidden as null
A count of zero comes back as null; the read also builds a readable label (“N users found this helpful”) which is null when the count is zero.

Scope

Own gateway allowlist
A separate list of ~30 approved callers, not shared with the rating-submit allowlist.
Reuses the Supplier Rating controller
The write-back is a distinct branch of the same UpdateRating code path that admin review and supplier replies use.
No cron, no supplier notification
Purely event-driven; the supplier is never told a vote happened.
GLID
GlobalID — the unique internal identifier for the voting buyer.
