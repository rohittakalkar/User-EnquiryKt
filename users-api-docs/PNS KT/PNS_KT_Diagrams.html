PNS — Virtual Number Pool

PNS manages a shared pool of virtual GSM (“IM_GSM”) numbers that mask a supplier's real phone. One write endpoint drives the whole lifecycle through a single numeric ACTION code: add a number to the pool, re-flag one, allocate one to a supplier, release one back, or bulk-convert many. Allocation and release both call the standard user-update API to actually attach or clear the number on the supplier. The replication queue is commented out, so the auth / search copies of the pool drift; a separate deletion-reason queue is live and feeds an audit table.

PNS — Virtual Number Pool

POST serviceName GSM_MASTER_SERVICE (~33-gateway allowlist). ACTION 1 = add to pool, 2 = re-flag, 3 = assign / auto-allocate, 4 = release, 5 = bulk-convert (loop, LIMIT 1–49, one query per iteration). FLAG_IS_AVAILABLE: 2 = available, 1 = assigned, 0 / -1 = two reclaimable buckets chosen by PNS_TYPE. Reads: /obdnumber (resolves the supplier's glusr_usr_im_gsm to a vendor type via a local JSON file) and /wservce/glmaster/detail (detail_from=gl_gsm_master).

Business flowchart

A pool of virtual GSM numbers, leased to suppliers

Everything routes through one ACTION switch:

  • ACTION 1 — add to pool: a new number row is inserted with FLAG_IS_AVAILABLE=2 (available).
  • ACTION 2 — re-flag: an existing number's availability flag is changed in place.
  • ACTION 3 — assign: a specific number, or an auto-allocated one (a random available row for the supplier's vendor type). If the row picked was already assigned to someone, userupdate_pns_allocation swaps old → new by calling the downstream user-update API.
  • ACTION 4 — release: calls the downstream user-update API with an empty IM_GSM. Only if that downstream call fails is the number flagged -1 locally, and an error email goes to the PNS team.
  • ACTION 5 — bulk-convert: loops over up to 49 suppliers, one query each.

A live PNS_DELETION queue records why a number was freed (PNS_DELETION_REASON audit table); the main replication queue is commented out.

Where a virtual number is claimed, freed and looked up

One master pool table, one dead replica path, one live audit path:

  • 1.0 Pool write applies the ACTION to D1 (the GSM master pool).
  • 2.0 User-update call-out attaches or clears the number on the supplier via the standard user-update API for ACTION 3 / 4.
  • 3.0 Replica consumers would mirror the pool into the auth / search copies — but the publish is commented out, so D2 drifts.
  • 4.0 Deletion-reason consumer writes the PNS_DELETION_REASON audit table D3.
  • 5.0 Reads resolve a supplier's OBD number and dump a pool row.

Sequence diagram · Actions 3 + 4

Allocating a virtual number, then releasing one

An allocation followed by a release:

  1. An internal tool calls the write API with ACTION=3; after the gateway check it picks a specific or random available number for the vendor type.
  2. alt — if the chosen row was already assigned, the old holder's number is swapped out via the user-update API; otherwise it is attached directly.
  3. The pool row is flagged assigned; a PNS_DELETION row for the previous supplier is removed.
  4. Later, ACTION=4 calls the user-update API with an empty IM_GSM. alt — on downstream success the number returns to the pool; on failure it is flagged -1 and the PNS team is emailed.

Glossary

Business terms used above.

The pool

PNS
Privacy Number Service — a pool of virtual GSM numbers that sit in front of a supplier's real phone so buyers never see the real number.
IM_GSM
The virtual number attached to a supplier (glusr_usr_im_gsm). Allocating sets it; releasing clears it.
GL_GSM_MASTER
The master pool table — one row per virtual number, with an availability flag and a vendor type.
FLAG_IS_AVAILABLE
2 = available, 1 = assigned, 0 / -1 = two “reclaimable” buckets. Which reclaimable bucket is used is chosen by PNS_TYPE.
Vendor type
The telecom vendor a number belongs to; auto-allocation only picks a random row matching the supplier's vendor type.

The actions

ACTION 1 — add
Insert a fresh number into the pool as available.
ACTION 2 — re-flag
Change an existing number's availability flag without moving it.
ACTION 3 — assign
Give a supplier a specific number, or auto-allocate a random available one. A swap via the user-update API happens if the chosen row was already held.
ACTION 4 — release
Clear the number off the supplier through the user-update API. The number only gets flagged -1 locally if that downstream call fails.
ACTION 5 — bulk-convert
A loop over up to 49 suppliers, one query per iteration.

Downstream & reads

PNS_DELETION_REASON
An audit table written from the live PNS_DELETION queue when a number is released with a reason; an ACTION 3 re-assign deletes that supplier's row.
Starved replicas
The auth / search copies of the pool are kept by a consumer whose publish is commented out, so they drift from GL_GSM_MASTER.
/obdnumber
A read that resolves a supplier's virtual number to a vendor type and then to an outbound-dialler number via a local vendor_obdnumber.json file.
OBD number
Outbound-Dialler number — the number the platform's call system dials from when connecting a buyer and supplier.
GLID
GlobalID — the unique internal identifier for the supplier.
