PNS Setting

PNS Setting stores a supplier's off-hours call-routing preferences — which of their mobiles, landlines or additional-contact numbers should still receive calls outside business hours (IIL_PNS_SETTING). One POST /pnssetting endpoint inserts, updates or deletes a mapping per number-type. The contact number is always re-derived server-side from the profile, never trusted from the request. A separate consumer auto-re-syncs these preferences whenever the supplier changes a phone number in the general profile-edit flow, and that path — unlike the direct API — enforces a five-mapping cap.

Telephony & Privacy

PNS Setting

POST /pnssetting serviceName PNS_SETTING_SERVICE (gateways GLADMIN / MAPI / BUYERMY / SELLERMY / ANDROID / IOS). Types M1 / M2 / L1 / L2 are general (no contact id); M / L / T are additional-contact and need a contact id; D is a sentinel (action_flag="d") that deletes all rows for a (supplier, contact) pair. offhrs_flag is 1 / 2 / 3 for insert / update and 0 for delete; reads treat 2 / 3 as “off-hours active”.

Business flowchart

Which numbers ring after business hours

One endpoint, several type families:

  • The GSM must already exist for the supplier, or the request fails with “GSM Number does not exist”. The contact number is always re-derived from GLUSR_USR / GLUSR_USR_ADDT_CONTACT; a non-numeric result becomes “INVALID”.
  • General types (M1/M2/L1/L2) carry no contact id; additional-contact types (M/L/T) require one.
  • A number can only map to one type. If the same number arrives under a second type, HandleDuplicatePnsUpdate keeps the row with the higher (or equal) offhrs_flag and silently deletes the other.
  • Insert is ON CONFLICT DO NOTHING plus an explicit “is this mapping already there?” pre-check.
  • The max-five-mappings cap is disabled in this write API but enforced in the auto-sync consumer (Flow C).
  • Only delete writes an audit trail; insert / update do not.

Data-flow diagram · Level 1

Where an off-hours routing preference is written and read

One table, one auto-resync consumer, one delete-cascade queue:

  • 1.0 Validate & write re-derives the number, resolves the type and inserts / updates / deletes D1.
  • 2.0 Duplicate-number resolver collapses a number that appears under two types, keeping the higher offhrs_flag.
  • 3.0 Auto-resync consumer re-calls /pnssetting over HTTP when the general profile-edit flow changes a phone number, enforcing the five-cap.
  • 4.0 Delete-cascade queues an IIL_PNS_SETTING delete when an additional contact is removed.
  • 5.0 Reads return one supplier's full detail, or a bulk check of which GLIDs have an active off-hours flag.

Sequence diagram · Flow A + C

Saving an off-hours preference, and the auto-resync

A direct save, then an automatic re-sync:

  1. The API checks the gateway, confirms the GSM exists, and re-derives the contact number from the profile (never from the request).
  2. alt — insert / update (offhrs_flag 1–3) runs ON CONFLICT DO NOTHING after a pre-check; delete (offhrs_flag 0, or the D sentinel) removes rows and writes the only audit trail this feature keeps.
  3. If the same number now maps to two types, the lower-flag row is dropped.
  4. Later, the supplier changes a mobile in the general profile-edit flow; the USER_UPSERT_ADDITIONAL consumer calls /pnssetting again over HTTP to re-sync, and here the five-mapping cap is enforced.

Only delete writes history; the exact meaning of offhrs_flag 1 vs 2 vs 3 is an open question, and the contact-deletion cascade into IIL_PNS_SETTING is queued, not transactional — all flagged in the source doc.

Glossary

Business terms used above.

The preference

Off-hours routing
Whether a given number keeps ringing outside business hours. That is the only thing this feature decides.
IIL_PNS_SETTING
The table holding one row per (supplier, number-type, contact) mapping.
offhrs_flag
1 / 2 / 3 mean insert-or-update (all three are “set” values); 0 means delete. Reads treat 2 and 3 as “off-hours active”.
Re-derived contact number
The actual phone number is always read back from the profile tables server-side; the number in the request is never trusted. A non-numeric result is stored as “INVALID”.
GSM must exist
The supplier must already have a virtual GSM number, or the request is rejected with “GSM Number does not exist”.

Number types

M1 / M2
Primary and alternate mobile — general types, no contact id needed.
L1 / L2
Primary and secondary landline — general types, no contact id needed.
M / L / T
Additional-contact mobile / landline / tollfree — each needs a contact id.
D sentinel
Not a real type; with action_flag="d" it deletes every mapping row for a (supplier, contact) pair at once.
Duplicate-number resolution
A number can map to only one type; if it turns up under two, the row with the higher (or equal) offhrs_flag survives and the other is silently deleted.

Automatic sync & reads

Auto-resync (Flow C)
When a supplier changes a mobile / landline / GSM in the ordinary profile-edit flow, a USER_UPSERT_ADDITIONAL consumer re-calls /pnssetting over HTTP so the preferences follow the new number.
Five-mapping cap
A limit of five active mappings per supplier — enforced only on the auto-resync path, not on direct API calls.
Delete-cascade
Removing an additional contact elsewhere queues a delete of its IIL_PNS_SETTING rows; there is a brief window where the contact is gone but its mapping is not.
Bulk read
Up to ten comma-separated GLIDs; the response says which of them have an off-hours flag of 2 or 3.
GLID
GlobalID — the unique internal identifier for the supplier.
