Knowledge Transfer · Engineering

Trust Verification

A generic, reusable framework for marking any supplier attribute — mobile, email, GST, PAN, CIN, TAN, bank account, address — verified or unverified, and reading the status back. Both manual (a call-centre agent) and automated (system-triggered) verifications flow through one write endpoint. Every change fans out to a notify queue and replicas; mobile verification expires after one year. A separate, adjacent path writes straight into the Trust database.

Trust & Compliance

Trust Verification

POST /user/verification is action_flag-driven: verify, bulk-verify or unverify. Sources carry a priority ranking (user / OTP outranks tactical), the write updates IIL_VERIFICATION_DETAILS plus a sharded GL_HISTORY audit row, and for mobile / email also the authpg dates. The adjacent /user/userverificationdetails writes trustpg directly with no fan-out and its own attribute-ID numbering.

Business flowchart

One framework to verify any attribute

The main write branches on action_flag:

  • Verify — after a gateway check and an optional cross-check of the submitted value against the live DB (a mismatch is logged, not always fatal), the source and its priority are resolved. A tactical / system source uses an anti-downgrade MERGE; a user / OTP source does a plain upsert. An audit row is written, and for mobile / email the authpg verification date is updated.
  • Bulk-verify — enqueues and loops per attribute.
  • Unverify — for OTP-tracked attributes the OTP record is cleared first, then the row is deleted and audited.

Reads pick the winning slot (user / tv over tactical); a mobile verification older than a year is forced to Not Verified. The adjacent Trust-DB write validates a primary plus secondary attributes against a separate group map and calls a trustpg stored function.

Where verification state, audit and replicas live

One primary store, an audit shard set, and downstream replicas:

  • 1.0 Validate checks the gateway whitelist and cross-checks submitted values via the gl_attribute mapping.
  • 2.0 Verify resolves the source priority and merges / upserts D1, writing an audit row to D2; 3.0 Unverify deletes and clears the OTP record in D3.
  • 4.0 Bulk verify loops 2.0 per attribute.
  • 5.0 Notify fan-out publishes the change; a consumer replicates it.
  • 6.0 Read serves status; 7.0 is the adjacent path that writes D4 (trustpg) directly.

Sequence diagram · Flow A

Verifying a single attribute, call by call

A single verify, from trigger to fan-out:

  1. The API checks the gateway whitelist, then cross-checks the submitted value against the live column resolved through gl_attribute.
  2. It resolves the source and priority, then merges (tactical / tv, anti-downgrade) or upserts (user / OTP) the verification row and writes a GL_HISTORY audit row.
  3. alt — if the attribute is mobile or email, the authpg verification date is updated.
  4. The change is published to the notify queue; a consumer replicates it downstream.

Glossary

Business terms used above.

The verification model

Attribute ID
A numeric ID per attribute type (mobile, email, GST, PAN, CIN, TAN, bank, address...) from a shared reference system consistent across the user domain.
Verified / Not Verified
Whether a valid verification record exists — or, for mobile, whether that record is still within a year.
Source priority
Verifications rank by source: user / OTP-driven outranks tactical / system. A third “tv” slot sits above both. A higher slot is only overwritten by an equal-or-higher priority (anti-downgrade MERGE).
Mobile 1-year expiry
A mobile verification older than 365 days is treated as Not Verified at read time; the record is not deleted, only the displayed status changes.
Multi-value attributes
Some attributes (e.g. bank account) can have several independent verification states, one per reference id — not a single flat status.
Live-value cross-check
If the caller also sends the current value, it is compared against the live DB column resolved through gl_attribute; a mismatch is logged.

Triggers

Manual verification
A call-centre agent confirms an attribute from a GLADMIN screen; the channel (screen / agency / IP / URL) is recorded.
Automated verification
An internal system marks an attribute verified when its own trigger completes (e.g. a GST BI match).
Android auto-verify shortcut
An Android-originated email-verify request auto-creates a synthetic OTP-style confirmation row without an actual OTP flow — a trusted-client shortcut.
Loopback
Background consumers call this write API over HTTP with a shared internal key rather than maintaining their own verification tables.
Bulk verify
A dedicated action_flag that processes many attributes for one GLID in a loop, sharing the same notify queue.

Two write paths

Main path
POST /user/verification — writes IIL_VERIFICATION_DETAILS plus a GL_HISTORY audit shard and fans out to the notify queue.
Adjacent path
POST /user/userverificationdetails (WEBERP / SOA-WAPI only) — writes the Trust database directly via a stored function, with no fan-out and its own attribute-ID numbering.
Trust DB replica
A separate physical database that verification events replicate into, so trust / compliance reads are independent of the primary store.

Access & audit

Gateway whitelist
A fixed list of ~24 approved caller identities for the main write API; the adjacent path allows only WEBERP and SOA-WAPI.
GL_HISTORY audit shards
The audit trail, sharded 100 ways by glid % 100, recording who / what / when / how for every verify or unverify.
GLID
GlobalID — the unique internal identifier for the supplier whose attributes are being verified.
