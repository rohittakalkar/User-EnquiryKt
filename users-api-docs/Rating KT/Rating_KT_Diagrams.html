Knowledge Transfer · Engineering

Supplier Rating

A buyer's 1–5 star + comment + thumbs on Response / Quality / Delivery + optional photos, against a supplier. Submit is instant, but the rating lands hidden; a topic-exchange fan-out then triggers roughly six background consumers (moderation, matchmaking check, enrichment, aggregate, notification, LMS sync) plus a Kafka seller-risk signal. A daily fraud / suspect cron re-scans still-pending ratings for rings. Only the latest rating per buyer-supplier pair stays live.

Ratings & Reviews

Supplier Rating

Display status starts at -2 (hidden). The matchmaking consumer sets -1 when no genuine connection is found; the suspect cron sets -1 / 0 by fraud flag. Every admin / system review — matchmaking, cron or GLADMIN — goes through the same IS_ADMIN write path, which always re-triggers the aggregate recompute.

Business flowchart

Instant submit, a heavily-checked publish

The main path is a submit; almost all the work is async:

  1. The buyer submits stars, comment, thumbs and photos. The API checks 1–5, buyer ≠ supplier, and the gateway.
  2. An existing-relationship check marks the rating new or an update, then GLUSR_RATING is inserted at display status -2 (hidden), with detail and photo rows.
  3. SUPPLIER_FEEDBACK is published to a topic exchange; the buyer sees “done” immediately.
  4. The fan-out runs in parallel: a CBS + PII + ML moderation cascade; a matchmaking check that hides the rating (-1) if no genuine connection; category enrichment; an aggregate recompute; a push notification; and two LMS sync paths. A Kafka signal feeds seller-risk scoring for fresh inserts.
  5. Over the next day or two the suspect cron re-scans pending ratings, runs a ring check via a fraud-graph API, and writes any verdict back through the IS_ADMIN path.

A supplier reply re-runs moderation on the reply text; archival keeps only the latest rating per pair.

Data-flow diagram · Level 1

Where a rating flows across ~9 background processes

One write, a wide fan-out:

  • 1.0 Validate & write checks the rules and writes D1 (rating + details + docs) at status -2, then publishes.
  • 2.0 Moderation screens content via external CBS / PII / ML APIs; 3.0 Matchmaking reads D3 and hides the rating if unconnected.
  • 4.0 Aggregate fully recomputes D2; 5.0 Notification pushes to the supplier; 6.0 LMS sync feeds a sharded LMS queue.
  • 7.0 Seller-risk emits a Kafka signal; 8.0 Suspect cron scans pending ratings and writes verdicts back; 9.0 Read serves the profile page.

Sequence diagram · Flow A

Submitting a rating and its background fan-out

A fresh submit and its parallel fan-out:

  1. The API validates 1–5, buyer ≠ supplier and the gateway, reads the existing-relationship count, and inserts the rating at display status -2 with detail and doc rows.
  2. It publishes SUPPLIER_FEEDBACK and returns to the buyer immediately.
  3. par — independent consumers run: moderation (CBS / PII / ML), matchmaking check (contact-book, sets -1 if unconnected), aggregate recompute, push notification, LMS sync.
  4. Later, the suspect cron computes a fraud verdict and writes it back through the IS_ADMIN path, refreshing the aggregate.

Glossary

Business terms used above.

Rating & visibility

1–5 star + comment
The core rating. Rejected outside 1–5, or if buyer and supplier are the same account.
Thumbs on Response / Quality / Delivery
Optional per-parameter up / down votes stored as separate detail rows.
Display status
-2 = hidden (the default on submit), -1 = disabled, a positive value = visible. The value that means “fully approved” is not written explicitly anywhere in code.
Two-layer fraud protection
A real-time matchmaking check (hides ratings with no genuine buyer-supplier connection) and a daily suspect cron (deeper cross-buyer ring detection). A rating visible on day one can be hidden on day two.
Latest-only per pair
When a new rating arrives for the same buyer-supplier pair, older ones are moved to an archive table; only the newest stays live.
Reply re-moderated
A supplier's reply goes through the same CBS / PII / ML moderation as the buyer's original comment.

The background pipeline

SUPPLIER_FEEDBACK fan-out
A single topic-exchange publish that up to six consumers bind against: moderation, matchmaking, enrichment, aggregate, notification, LMS sync.
Content moderation
A CBS banned-keyword check + PII detection + an ML abuse model, run as an API-call-minimising cascade; a flagged field is hidden via a callback into the write API.
Matchmaking check
Reads the contact-book mapping to confirm the buyer and supplier were genuinely connected; sets display status -1 if not.
Aggregate recompute
A supplier-wide rollup of star counts and parameter counts, fully recomputed on every insert, admin action, archival and the 91-day cron.
IS_ADMIN write-back path
The single path used by admin review, the matchmaking consumer and the suspect cron to change a rating's status — it always re-triggers the aggregate recompute.
Seller-risk signal
A Kafka message per fresh rating feeding a separate supplier risk-scoring pipeline.
Two LMS sync paths
An inline packet inside the feedback message and a separate dedicated consumer publishing into a sharded LMS queue set.

The suspect cron

Daily suspect scan
A batch job over still-pending ratings from the last day or two.
fn_get_rating_suspect_flag
A DB function returning a suspect flag per rating; the cron maps flags to display-status actions by priority.
Ring detection
For a supplier with several same-day ratings, the cron calls a fraud-graph API pairwise across the rating buyers; 3+ connected pairs flags the group.
91-day aggregate cron
A separate scheduled job that forces an aggregate recompute for ratings turning 91 days old, so time-decayed averages stay current.
GLID
GlobalID — the unique internal identifier for the buyer or supplier.
