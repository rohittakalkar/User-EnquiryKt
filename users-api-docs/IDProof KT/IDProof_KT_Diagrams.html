Knowledge Transfer · Engineering

ID Proof

A supplier submits one identity-document number plus a proof image / URL per proof-type. It is a single-table record with a binary status — 0 pending, 1 approved. Insert-or-update is auto-detected per (supplier, proof-type); updates are partial. There is no notification, queue, consumer or cron — the whole feature is one synchronous request and response.

Trust & Compliance

ID Proof

One write endpoint handles both insert and update, deciding by whether a record already exists for the supplier + proof-type. There is no explicit rejected status, and no code path was found that moves the status from 0 to 1 — approval is assumed to be a manual admin action.

Business flowchart

One document number, one proof image, one status

Write and read are both a single round-trip:

  1. The supplier picks a proof-type and sends a number and a document reference.
  2. The caller must be on the gateway allowlist — GLADMIN, MAPI, Android or iOS.
  3. If a record already exists for that supplier + proof-type it is a partial update: fields not sent keep their stored value, and the approval status is retained unless explicitly sent.
  4. If not, a new record is inserted with status 0 (pending).
  5. A read returns the number, document reference and status, or “No data found”.

Data-flow diagram · Level 1

Where the ID-proof record is written and read

Two processes, one store:

  • 1.0 Validate & upsert checks the gateway allowlist and field rules, reads D1 to see whether a record exists, then inserts or partially updates it.
  • 2.0 Read ID-proof returns the stored number, document reference and approval status for a supplier + proof-type.

No queue, consumer or downstream fan-out exists in this feature.

Submitting and reading an ID proof

Submit then read, on one table:

  1. The write API validates the gateway and fields, then reads the existing record for the supplier + proof-type.
  2. alt — if it exists, a partial update (fields absent are kept, status kept unless sent); otherwise an insert with status 0.
  3. A later read returns the number, document reference and status, or “No data found” if there is no record.

Glossary

Business terms used above.

The record

ID proof
One government-issued identity-document number plus a reference to its supporting image / URL, held against the supplier.
Proof-type
The category of document (e.g. identity proof, address proof). A supplier can have one independent record — and one status — per proof-type.
Document reference
The URL or image reference for the supporting document. Stored, not validated for content.
Approval status 0 / 1
0 = pending (the default on insert), 1 = approved. There is no rejected value.
Insert-or-update (auto-detected)
One endpoint handles both; it decides by whether a record already exists for the supplier + proof-type.
Partial update
On update, any field not sent keeps its stored value — including the approval status, which is only changed if explicitly provided.

Access

Gateway allowlist
The callers allowed to write: GLADMIN, MAPI, Android, iOS.
Validation key
The shared key each caller sends to authorise the write.
GLID
GlobalID — the unique internal identifier for the supplier the ID proof belongs to.

Not present in the code

No rejected status
The write path accepts only 0 or 1. Any rejection concept is handled elsewhere or by deleting the record.
No notifications
Nothing is emailed, texted or pushed on submit, update or approval — unlike GST.
No background review
No consumer or cron was found that moves a record to approved; approval is assumed to be a manual admin action.
