Knowledge Transfer · Engineering

User Add / Update

User Add / Update is the foundation of the whole users domain: the master GLUSR_USR record for every supplier and buyer is created and edited here, and almost every other KT feature attaches its data to this record. Add prevents duplicate accounts (by mobile, email and business-registration number) and, on a match, fills only the gaps of the existing account rather than creating a new one. Update is a partial edit that can per-attribute un-verify a TrustSeal when sensitive fields change, and every write fans out to fifty-plus downstream systems.

Core Identity

User Add / Update

Two controllers: GLUSR_INSERT_SERVICE (Add) and GLUSR_UPDATE_SERVICE (Update). Add runs a three-signal duplicate check (CheckUniqueMesh → M1 / E1 / G1); zero matches take the true-insert path (INSERT … ON CONFLICT DO NOTHING, APPROV="A") plus a sequential InsertAuthPG write; any match takes a six-branch resolver that gap-fills the existing account via an internal HTTP loopback. Update builds a dynamic partial UPDATE GLUSR_USR, strips TsNoUpdateVerify fields for TrustSeal callers, computes per-attribute un-verification (att_id), writes authpg, and publishes GLUSR_UPDATE_SERVICE or GLUSR_UPDATE_CRON_SERVICE to a large consumer fan-out.

Business flowchart

The source of truth for every user account

Two flows over one master record:

  • Flow A / B — Add: the request is checked against three identity signals — mobile, email and GSM (business-registration number), mobile winning on conflict. No match → a brand-new account is created (immediately Approved) and its login credentials are written to a second database. A match → no new account; the existing one is gap-filled — only its empty fields are populated, existing values are never overwritten, and a conflicting email is rejected.
  • Flow C — Update: a partial edit; only changed fields are processed. Changing a sensitive field (company name, address, phone, designation, turnover …) per-attribute un-verifies the TrustSeal for that field; a location change also raises a location-un-verification. A TRUSTSEAL- sourced update is treated specially — it does not self-un-verify, and it cannot touch already-verified address / mobile / email fields at all (they are stripped from the request).
  • Both flows fan out asynchronously to 50+ systems; automated bulk updates (UPDATEDBY = "GLUSR Manual cron") go down a separate lane.

Data-flow diagram · Level 1

Where the master user record is created, edited and fanned out

Two databases written synchronously, a huge async fan-out:

  • 1.0 Add runs the three-signal duplicate check against D1, then either inserts a new GLUSR_USR row or, via 2.0 gap-fill loopback, updates the matched account.
  • 3.0 Update fetches the old row, strips TrustSeal-locked fields, and writes a dynamic partial update to D1.
  • 4.0 Auth mirror writes the smaller credential set to D2 (authpg) on every add and update.
  • 5.0 Fan-out publishes one event consumed by 50+ downstream systems (verification, trust, alert, enquiry, LMS, search …), with a separate cron lane.

Sequence diagram · Flows A + C

Creating an account, and editing a profile with TrustSeal impact

A new registration, then a profile edit:

  1. Add validates mandatory fields, then checks mobile / email / GSM for an existing account.
  2. alt — no match: a new GLUSR_USR row is inserted (auto-approved), credentials are written to authpg, and the insert event is published. A match: the existing account is gap-filled through an internal loopback and no new row is created.
  3. Later, Update fetches the old row and, for a TRUSTSEAL caller, strips address / mobile / email fields.
  4. alt — a sensitive field changed: its attribute id is added to the un-verification payload; otherwise the update is plain. The auth mirror is written and the update event is published to the normal or cron lane.

Glossary

Business terms used above.

The master record

GLUSR_USR
The master user / company record for every supplier and buyer. Almost every other KT feature attaches its data to this record's id.
Add vs Update
Add creates the record at signup (GLUSR_INSERT_SERVICE); Update edits it afterwards (GLUSR_UPDATE_SERVICE). Both are partial and dynamic — only supplied fields are written.
Auto-approved
A new account is created directly in the Approved state (APPROV = "A"); any moderation happens later via downstream processes.
Dual-DB write
Every add and update also writes a smaller credential set to a separate auth database; the two are kept in sync, sequentially, with no cross-database rollback.

Duplicate handling

Three identity signals
Duplicate detection runs on mobile, email and GSM (business-registration number). Mobile wins over email over GSM when they point to different accounts.
Gap-fill merge
On a duplicate match no new account is created; only the existing account's empty fields are filled from the new data. Existing values are never overwritten.
Email conflict
If the new email differs from a non-empty email on the matched account, the request is rejected with “Primary Email id already exist”.
Internal loopback
The six-branch duplicate resolver reaches the update logic through an internal HTTP call to the update endpoint, not a direct in-process call.

TrustSeal & fan-out

Per-attribute un-verification
Changing a TrustSeal-sensitive field (company name, address, phone, designation, turnover, employee count, legal status, name …) marks the TrustSeal for that specific attribute as stale — not a single account-wide flag.
Location un-verification
A city / state / geo change additionally raises a separate location-un-verification and includes the lat-long attribute ids.
TRUSTSEAL-sourced update
A write from the TrustSeal screen does not self-un-verify the field it is writing, and cannot change already-verified address / mobile / email fields at all — those keys are stripped before any SQL runs.
Cron lane
When UPDATEDBY is exactly "GLUSR Manual cron", the event is published to GLUSR_UPDATE_CRON_SERVICE so downstream systems can treat bulk / automated updates differently.
50+ fan-out
One GLUSR_USR write is consumed by many downstream copies — verification, trust, alert, blacklist-display, enquiry, LMS, CSL / search — all asynchronous.
GLID
GlobalID — the unique internal identifier for the user; GLUSR_USR_ID is the primary key returned on insert.
