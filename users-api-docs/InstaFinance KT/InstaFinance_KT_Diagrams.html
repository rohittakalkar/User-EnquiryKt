Knowledge Transfer · Engineering

InstaFinance

InstaFinance is a single on / off switch on a registered company's record — keyed by its CIN, not by any supplier account — that marks whether financial / lending services are enabled for that company. Only one internal app may call it, it can only update a company that already exists, and every successful change also queues a background re-apply of the same update so it cannot silently go missing. Nothing in the reviewed code reads the flag; the downstream lending system that consumes it lives elsewhere.

Financial Services

InstaFinance

POST /instafinance (gateway MY only — the narrowest allowlist in the KT series). It runs UPDATE COMP_MASTER_FINANCIALS SET COMP_MASTER_FINANCIAL_ENABLED = $1 WHERE COMPANY_CIN = $2 on meshpg; the flag must be 0 (enabled) or -1 (disabled), the CIN exactly 21 characters. Zero rows affected → “no record found” and no event. On a real update a RabbitMQ message (INSTAFINANCE → user.insta.<glid % 20>) drives a consumer that re-runs the same UPDATE; a failure there is re-queued.

Business flowchart

One company-level financial-services switch

One flow, with a safety net:

  • An internal tool submits a CIN and a target flag value (0 or -1).
  • The system updates the company's existing financial record. If the CIN has no record, it returns “no record found” — this endpoint never creates one.
  • On a successful update, a background sync is queued that re-applies the same change, so a transient miss downstream gets retried automatically.
  • The flag is company-level: one CIN covering several accounts flips for all of them at once.

Where the eligibility flag is toggled and re-synced

One table, one synchronous write, one async re-apply:

Sequence diagram · Flow A

Toggling the flag, with the background re-apply

The toggle and its background re-apply:

  1. The internal tool posts a CIN and flag value; the API checks the MY gateway, the flag value and the 21-character CIN.
  2. alt — the UPDATE affects zero rows: the API returns “no record found” and publishes nothing. Otherwise it publishes an INSTAFINANCE message.
  3. The consumer re-runs the same UPDATE.
  4. alt — that succeeds and is acked; or it fails and the message is re-queued for another attempt.

Glossary

Business terms used above.

The switch

InstaFinance
IndiaMART's financial-services / lending offering; this feature is only the eligibility toggle in front of it.
CIN
Corporate Identification Number — the 21-character registration id of an Indian company. The flag is keyed on this, not on a supplier login.
COMP_MASTER_FINANCIAL_ENABLED
The flag itself: 0 means enabled, -1 means disabled. Any other value is rejected (with a misleadingly-worded “length” error).
Company-level
One CIN can span several supplier accounts; toggling the flag affects all of them together.
Update-only
The endpoint can only change an existing company record; it never creates one. A missing CIN returns “no record found”.

The safety net

Background re-apply
Every successful toggle publishes a message whose consumer re-runs the identical UPDATE, so a downstream miss is retried automatically.
INSTAFINANCE queue
The RabbitMQ service name; it resolves to a sharded route user.insta.<GLID % 20>, so an absent GLID lands everything on shard 0.
Requeue
If the consumer's UPDATE fails, the whole message is re-published to a retry queue rather than dropped.
Shared consumer
The worker that handles these messages (USER_UPSERT_ADDITIONAL_GCP_IN) also processes unrelated verified-badge messages.
GLID
GlobalID — the supplier identifier; here it is optional and only used for shard routing and the message payload.
