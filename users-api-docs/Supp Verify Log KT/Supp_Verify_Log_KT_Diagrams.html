Supplier Verification Log

An outcome log for supplier verification calls — verify flag, disposition, call counter, voice-log URL, up to five attachments. GLADMIN-only writes (INSERT / UPDATE / DELETE, with delete always audit-trailed). A nightly batch cron also populates entries from business signals — but of the nine rules in the code only four run; the other five are switched off or gutted. No queue, consumer or Redis; a Google Chat summary after every cron run.

Verification tooling

Supplier Verification Log

The write API is ACTION-driven. The cron reads mainpg / meshpg, applies four active rules, and mails a Google Chat summary. The read returns every log row for a supplier — no latest-only filter.

Business flowchart

Manual call outcomes, plus a half-live cron

Two ways rows get created:

  • Manual (GLADMIN) — INSERT a new log (call counter starts at 1), UPDATE by log id only (no ownership check), or DELETE by supplier + log id, which always calls the shared history-package audit.
  • Nightly cron — 4 active rules: recently-disabled supplier → mark Verified; PNS-defaulter → Verified if they paid, else Rejected (never touching a protected -3 row); recent receipt → remove from the calling queue; fraud-prone country → remove from the calling queue. Then a Google Chat summary, whether the run succeeded or failed.
  • 5 dormant / dead rules — free-verified downgrade, click-to-call, hot-lead, data-copy, QGFCP/VGFCP — look live in the code but are switched off or commented out.

The read returns all rows for a supplier, no pagination, on a 100 ms timeout.

Where verification outcomes and the calling queue are touched

The manual path is one table; the cron spans several:

  • 1.0 Manual write INSERT / UPDATE / DELETEs D1; 2.0 Delete audit always fires the history package into D4.
  • 3.0 Nightly cron reads mainpg sources (D3), writes Verified / Rejected rows into D1, and deletes entries from the calling queue D2.
  • 4.0 Summary mails Google Chat after every run.
  • 5.0 Read returns all log rows for a supplier.

Sequence diagram · Flow B

The nightly batch-populator cron

The nightly run, rule by rule:

  1. The scheduler starts the cron; it reads recently-disabled suppliers from mainpg and inserts Verified rows.
  2. It reads PNS-defaulters. alt — paid: write Verified (skipping any verify_flag = -3 row); not paid: write Rejected.
  3. It reads recent-receipt suppliers and deletes their calling-queue entries.
  4. It deletes fraud-prone-country entries from the calling queue.
  5. It posts a Google Chat summary — on success or failure.

Glossary

Business terms used above.

The log

verify_flag
The outcome code: -1 = Verified (paid catalog to FCP), -5 = Rejected (catalog PNS defaulter), -7 = free-verified downgrade (dormant), -3 = a protected state the PNS rule must not overwrite. No enum exists in code.
Disposition + activity
A reason / outcome label pair stored on each row (e.g. Verified / “Paid Catalog To FCP”).
Call counter
How many verification calls have been made; starts at 1 on insert.
Voice-log URL & attachments
A recording link and up to five comma-separated attachment references per row.
Insert masked as update
On a successful insert the response message is rewritten to say “UPDATE SUCCESS”; only the wording changes, not the status.

Manual write

GLADMIN-only
The only caller type allowed to write; suppliers never write this table.
ACTION INSERT / UPDATE / DELETE
The three operations. INSERT needs a verify flag; UPDATE and DELETE need a log id.
UPDATE by log id only
An update is matched on the log id alone, with no check that it belongs to the supplier in the request.
DELETE always audit-trailed
Every delete calls a shared history-package stored procedure, whether or not a row was actually removed.
verify_flag = -20
A special manual-insert case that additionally requires a REQUEST_URL as proof.

The nightly cron

4 active rules
Disabled-supplier → Verified; PNS-defaulter → Verified if paid else Rejected; recent-receipt → remove from calling queue; fraud-prone country → remove from calling queue.
5 dormant / dead rules
Free-verified downgrade (ready but switched off), click-to-call, hot-lead, data-copy, QGFCP / VGFCP (logic commented out). They look live in the code but do nothing.
Hard-coded 9-country list
The fraud-prone country rule matches an IP-country against a fixed list and removes that calling-queue entry the same day.
Google Chat summary
Every run posts a summary — counts by rule and source — on success or failure.
Calling queue vs outcome log
iil_supp_verification is the upstream calling queue (SellOnIM's domain); IIL_SUPP_VERIFICATION_LOG is this feature's outcome log. The cron touches both; there is no FK between them.
GLID
GlobalID — the unique internal identifier for the supplier.
