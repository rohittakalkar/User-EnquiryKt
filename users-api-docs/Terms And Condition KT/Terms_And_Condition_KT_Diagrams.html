Knowledge Transfer · Engineering

Terms & Condition Acceptance

When a supplier accepts IndiaMART's Terms & Conditions, the event is written as one append-only log row — who, from which IP and country, on which device, and when. There is no update, no dedup, no read API, no cron. On a successful insert a single session-update message is published, whose downstream effect is not visible in the reviewed repos. It is the simplest write flow in the KT series.

Legal & Compliance

Terms & Condition Acceptance

POST /user/tncacceptance (serviceName USER_TERMS_AND_CONDITIONS). The route is JWT-exempt, so a 33-entry Gateway_v1 allowlist is the only auth. Mandatory: MODID, VALIDATION_KEY, IP, USR_ID, USER_AGENT. One INSERT into IIL_TERMS_COND_ACCEPTANCE (meshpg, 1-second timeout); the date column is app-generated. On success a single RabbitMQ message (SERVICENAME = TNC_ACCEPTANCE, payload STATE = "9") is published direct-to-queue SESSION_UPDATE, no exchange.

Business flowchart

An append-only proof that T&C was accepted

One step, one outcome:

  • A supplier accepts the T&C through any allowed channel — web, app or an internal tool.
  • The API checks the caller is on the allowlist and the mandatory fields are present.
  • A fresh log row is written: user id, IP, IP country, country code, user-agent and date. Nothing is overwritten; a repeat acceptance simply adds another row.
  • On success a session-update event fires; the supplier gets no visible confirmation — it is a background compliance record.

Sequence diagram · Flow A

Recording a T&C acceptance

The whole feature in one exchange:

  1. An allowed channel posts the acceptance with the mandatory fields.
  2. The API validates and appends a row (the date is generated server-side).
  3. alt — insert succeeds: a single TNC_ACCEPTANCE message is published to SESSION_UPDATE; insert fails: no message, the error is logged only.

There is no dedup — a double-submit creates two rows; the SESSION_UPDATE queue has no consumer in the three repos and STATE = "9" is an unexplained magic value; validation is unusually lenient about unknown field names; and the controller file has a stray .go.go extension — all flagged in the source doc.

Glossary

Business terms used above.

The log

T&C acceptance
The event of a supplier agreeing to IndiaMART's Terms & Conditions — at signup or after a policy update.
IIL_TERMS_COND_ACCEPTANCE
The single append-only meshpg table; one row per acceptance event.
Append-only
Every acceptance is a fresh insert. Nothing is updated or overwritten, so the full history is always available.
No dedup
The code never checks for an existing acceptance, so a double-tap or retry creates multiple rows for the same logical event — harmless for an audit log, relevant if anyone counts acceptances.
Captured fields
User id (who), IP + IP country + country ISO (where), user-agent (which device), and an app-generated date (when).

Access & downstream

33-entry allowlist
A wide set of internal channels — web, mobile app, admin and telecalling tools — may record an acceptance. The supplier does not call the API directly.
JWT-exempt route
The endpoint skips the usual JWT / AK token check; the VALIDATION_KEY allowlist match is the only auth.
SESSION_UPDATE event
A single fire-and-forget message published on success, carrying STATE = "9". It is meant to update the supplier's session / status somewhere downstream; no consumer for it exists in the reviewed repos.
GLID
GlobalID — the unique internal identifier for the supplier.
