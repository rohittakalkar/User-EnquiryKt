Update With OTP

Update With OTP is a backend security gate, not a screen. When a supplier changes a sensitive contact detail (mobile, email) — or overrides a locked / verified field such as a Tactical-Verified GST — this feature requires two separate OTPs, each tied to an attribute context, verified strictly in sequence. It writes no profile data itself: once both OTPs pass, it strips the OTP fields and calls the standard /user/update API to perform the actual change. All the real write logic, and its downstream validations, live there.

Update With OTP

POST /user/updatewithotp serviceName UPDATEWITHOTP. Two SELECTs against glusr_usr_otp (authpg), no write of its own. OTP1_ATTR / OTP2_ATTR are "value$$attribute_id" strings; the attribute id resolves mobile vs email via a fixed map (EMAIL=109, EMAIL_ALT=157, PH_MOBILE=121, PH_MOBILE_ALT=48). Step 1 verifies OTP1; on success a metadata-only RabbitMQ audit event fires regardless of what Step 2 does. Step 2 verifies OTP2 against the new value; only then does TriggerRequest loop back into /user/update.

Business flowchart

A two-OTP gate in front of a normal profile update

A strict two-step gate:

  • Step 1 — OTP1_ATTR is split on $$; the attribute id decides whether the value is a mobile or an email; the stored OTP for that value is fetched and compared to OTP1. Not found → error; mismatch → reject, and Step 2 never runs.
  • The moment Step 1 passes, a metadata-only audit event is published to RabbitMQ — it carries no new field value and fires whether or not Step 2 later succeeds.
  • Step 2 — the new value is discovered by scanning the request for the first key that matches the attribute map. The stored OTP for that new value is compared to OTP2; additionally the value must equal OTP2_ATTR's value half, or it is rejected as “attribute value does not match”.
  • Both pass → TriggerRequest removes the OTP fields, token and modid, and POSTs the rest to the standard /user/update endpoint. A non-200 from there is re-wrapped as a generic 500.
  • Flow B — the same gate is the recognised “strong proof” a supplier uses to override a locked / verified field (e.g. GST) without GLADMIN help.

Data-flow diagram · Level 1

Where the two OTPs are checked and the update is delegated

A verification-only gate with an HTTP loopback:

  • 1.0 Mandatory / OTP-field checks validate the request shape.
  • 2.0 Step 1 reads glusr_usr_otp (D1) for the OTP1_ATTR value and compares.
  • 3.0 Audit publish emits a metadata-only event to user.additional.* right after Step 1.
  • 4.0 Step 2 reads D1 again for the new value and compares, including the value-match check.
  • 5.0 Loopback POSTs the cleaned payload to the external /user/update API, which owns the real write.

Sequence diagram · Flow A

A two-OTP verification, then the loopback update

The full happy path and its early exits:

  1. The API checks mandatory fields and that all four OTP keys are present and non-blank.
  2. Step 1 resolves mobile / email from OTP1_ATTR and compares the stored OTP with OTP1. alt — not found → 500; mismatch → 204 and stop.
  3. A metadata-only RabbitMQ audit event is published immediately.
  4. Step 2 finds the new value in the request and compares the stored OTP with OTP2. alt — not found, mismatch, or value-mismatch → reject.
  5. Both pass → strip OTP fields and POST to /user/update; its result is relayed back (non-200 becomes a generic 500).

Glossary

Business terms used above.

The gate

Two-factor OTP
Two separate OTPs, each tied to its own attribute context, must both pass. One OTP is never enough.
Sequential verification
OTP1 is checked first; only if it passes is OTP2 checked. A failed OTP1 means OTP2 is never evaluated.
Attribute context
Each OTP is bound to a specific field. OTP1_ATTR / OTP2_ATTR are "value$$attribute_id" strings; the id maps to EMAIL (109), EMAIL_ALT (157), PH_MOBILE (121) or PH_MOBILE_ALT (48).
Value-match check
For OTP2, the correct code is not enough — the value it was generated for must also equal the new value being submitted, or the request is rejected.
Verification-only
This feature writes no profile data. It confirms identity and then delegates the real change.

Delegation

TriggerRequest
After both OTPs pass, it strips OTP1 / OTP2 / *_ATTR / token / modid and POSTs the rest to the standard update API.
/user/update
The normal profile-update endpoint (GLUSR_UPDATE_SERVICE) that every other profile edit also uses; it owns the actual write and all downstream validation.
Re-wrapped error
A non-200 from /user/update surfaces to the caller as a generic 500, not the original error code — and the OTPs are already spent.
Metadata-only audit event
A RabbitMQ message published right after OTP1 succeeds. It carries no new value, fires even if OTP2 later fails, and has no consumer found in the repos.

Override use & cautions

Locked-field override (Flow B)
Once a field like GST is Tactical-Verified or OTP-Verified it cannot be changed by ordinary editing. Passing this two-OTP gate is the recognised supplier-side way to override that lock.
Tactical Verified
A GST-domain trust state where the number was verified via a background / tactical check; it locks the field against normal edits.
Echoed OTP codes
Every response includes the real stored OTP values (Otpredis1 / Otpredis2) alongside the submitted ones — flagged for security review.
GLID
GlobalID — the unique internal identifier for the supplier.
