Privacy Setting

Privacy Setting is a collection of independent switches over what a supplier shows publicly and which emails / alerts they receive. Each setting has its own id and its own default in a master catalogue, and the per-supplier table only ever stores the non-default state. A toggle fans out to a search replica, a denormalised quick-lookup flag on the user record (for five specific ids) and a compliance-critical email-unsubscribe list. Two special cases sit outside the normal path: email-frequency is forwarded straight to the email engine, and the read endpoint has three independently-evolved code paths.

Preferences & Compliance

Privacy Setting

POST /details with type=PrivSetting reads MY_PRIVACY_SETTING.MY_PRIVACY_DEFAULT_BEHAVIOR and whether a GLUSR_USR_PRIVACY_SETTING row exists, then inserts / deletes so the row records only the non-default state. Success publishes USER_DETAILS_SERVICE, which fans out to USER_PRIVACYSETTING_IMSDB (search replica) and USER_PRIVACYSETTING_ALERTPG (denormalised FK_MY_PRIVACY_SETTING_IDS for ids 45 / 90 / 20 / 153 / 175, plus GLUSR_EMAIL_UNSUBSCRIBERS). subCat=mail_frequency skips the DB entirely and publishes MAIL_FREQUENCY_ALERT. GET /setting branches on version / app version and on flag (0 / 1 proxy a write, 2 is the real read).

Business flowchart

Many small switches over visibility and email

One normal path and three special cases:

  • Flow A — normal toggle: the setting id resolves a default; a per-supplier row exists only to record the opposite of that default. So an “insert” can mean enabled for one setting and disabled for another. Every non-insert change writes an audit-trail row.
  • Flow C — email frequency: a preference change here is never stored in the privacy table; it is forwarded as a message to the email engine, which owns it.
  • Flow D — email unsubscribe: when a setting goes to Disabled with a recorded source, the supplier is added to the unsubscribe list; re-enabling removes them.
  • Flow E / F — read: GET /setting has three code paths chosen by client version, and its flag=0 / flag=1 values actually trigger a write via an internal call.

Where a privacy toggle is written and propagated

One primary write, a three-way fan-out, one bypass:

  • 1.0 Toggle write reads the default and the existing row from D1 / D2 and inserts / deletes D1, plus an audit row.
  • 2.0 Search-replica consumer mirrors the change into the search copy.
  • 3.0 Denormalised-flag consumer rewrites the comma-separated id list on D3 for five specific setting ids.
  • 4.0 Unsubscribe consumer inserts / deletes D4 based on the new value and source.
  • 5.0 Mail-frequency bypass publishes to the email engine with no DB write here.

Toggling a setting, and the email-unsubscribe fan-out

A toggle and its unsubscribe fan-out:

  1. The supplier flips a setting; the API reads the master default and whether a row already exists.
  2. alt — per the default-vs-requested truth table the API inserts a row, deletes one, or does nothing; a non-insert change also writes an audit row.
  3. Success publishes USER_DETAILS_SERVICE; consumers replicate to search and update the denormalised flag.
  4. alt — the unsubscribe consumer: new value Disabled with a source inserts / refreshes an unsubscribe row; Enabled deletes it.

Glossary

Business terms used above.

The model

Privacy setting
One independent switch over visibility (e.g. show my mobile) or communication (e.g. receive marketing email).
MY_PRIVACY_SETTING
The master catalogue: every setting id and its default behaviour (on or off for everyone).
Non-default-only storage
A GLUSR_USR_PRIVACY_SETTING row exists only when a supplier's choice differs from the default. No row means the supplier is at the default, not that data is missing.
Inverted action
Because rows record the non-default state, an INSERT means “enabled” for a default-off setting and “disabled” for a default-on one — confusing in logs, correct by design.
is_automated
Marks whether the last change was made by the system rather than the supplier; only maintained for a few specific setting ids.
Audit trail
Every non-insert change records who / when / from which IP via a history stored procedure.

The fan-out

Search replica
A consumer that mirrors each change into the search / directory copy so visibility settings affect search results.
Denormalised id list
For five setting ids (45, 90, 20, 153, 175) a comma-separated FK_MY_PRIVACY_SETTING_IDS column on GLUSR_USR is kept in sync for quick lookup without joining the settings table.
Email unsubscribe
When a setting goes to Disabled with a recorded source, the supplier is added to GLUSR_EMAIL_UNSUBSCRIBERS; re-enabling removes them. The compliance-critical part of the feature.
Mail frequency
A special preference that is never stored here — the request is forwarded to the email engine via a MAIL_FREQUENCY_ALERT message.

Reading settings

GET /setting
The read endpoint — but it has three code paths chosen by the version query param and the client's app version.
flag 0 / 1 / 2
2 is the genuine read. 0 and 1 make the read endpoint call the write API internally to enable / disable a setting.
UK signed link
An emailed “manage preferences” link carries a signed token valid for 7 days; the embedded email must match the account's, allowing access without a normal login.
Seller Assistant sub-details
Setting ids 1250 / 1248 / 1246 additionally carry a JSON blob (AI-chat / calling preferences) in the response.
GLID
GlobalID — the unique internal identifier for the supplier.
