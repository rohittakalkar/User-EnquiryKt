Knowledge Transfer · Engineering

Disposition

A disposition is an outcome / reason code. When an internal review or verification step finishes, its result is picked from a per-attribute master list and saved against the supplier — insert-only, so the full history is kept. The master list is generic across attributes; reading the history back currently works only for the GST attribute.

Verification tooling

Disposition

Three flows. Flow B — fetch the master list of enabled dispositions (any attribute) to populate a dropdown. Flow A — an internal tool records a chosen disposition as a new row in GLUSR_DISPOSITIONS. Flow C — read a supplier's disposition history, gated to GST only. No queue, consumer, cron or cache anywhere.

Business flowchart

Recording an outcome code against a supplier

The three flows are usually used in order:

  1. List — the tool fetches every enabled disposition, each with its attribute's display name. Open to any caller.
  2. Record — a tool on the allowlist (GLADMIN, SELLERMY, IMOB, MSITE) submits the chosen MASTER_ID against a GLID. The write is a blind INSERT — no check that the master ID matches the attribute name.
  3. Read back — if the attribute is GST, return the full history (all=1) or just the latest entry; any other attribute returns no data.

Data-flow diagram · Level 1

Where disposition data is written and read

All three processes are single round-trips:

  • 1.0 Read master list joins D2 and D3, returning every enabled disposition and its attribute name — no attribute filter, no gateway.
  • 2.0 Record disposition validates the allowlist, mandatory and length rules, then inserts one row into D1.
  • 3.0 Read attribute history short-circuits to “no data” unless the attribute is GST, then reads D1 joined to D2.

Sequence diagram · Flows B / A / C

List, record, and read back a disposition

List → record → read, across three endpoints that share no orchestration code:

  1. The tool reads the master list and shows the disposition text; the user picks one.
  2. The tool submits the matching MASTER_ID; the write API validates and inserts a new history row with no cross-check.
  3. alt — a history read for a non-GST attribute returns NO_DATA_FOUND before any query; for GST it returns all rows or just the latest.

Glossary

Business terms used above.

The disposition model

Disposition
An outcome / reason code recorded against a supplier when an internal review or verification step finishes.
Disposition master list
The curated set of valid disposition codes, each tied to one attribute. Only enabled entries appear in dropdowns.
Attribute
What the disposition is about — e.g. GST. The master list is multi-attribute by design.
MASTER_ID
The ID of the chosen row in the disposition master list. This is what actually gets stored on the supplier's record.
MODID
The identity of the tool / system that recorded the disposition, stored for the audit trail.
Insert-only / history-preserving
Every submission creates a new row; nothing is overwritten, so the full outcome history per supplier is kept.

Reading it back

Attribute-history read (GST only)
The endpoint that returns a supplier's disposition history. It short-circuits to “no data” for any attribute other than GST, even though the master list is generic.
all flag
On the history read: all=1 returns every row; anything else returns only the latest disposition.
ENABLED = -1
This codebase's convention for “true / enabled”. A disposition with any other value is hidden from the dropdown without being deleted.

Access

GLID
GlobalID — the unique internal identifier for the supplier the disposition is recorded against.
Write allowlist
Only GLADMIN, SELLERMY, IMOB and MSITE may record a disposition. Reading the master list has no allowlist at all.
