Buyer Blocking

Any user — supplier or buyer — can block another user so they are never contacted again. It is a single, silent, reversible database row. The one confirmed enforcement point: on the Buyer Profile screen, if a buyer has blocked a supplier, that supplier sees the buyer's contact details and verification status blanked out.

Buyer–Seller Discovery

Buyer Blocking

Two flows. Flow A — a user submits a block or unblock, which is one INSERT ... ON CONFLICT DO UPDATE on USER_BLOCKED_STATUS. Flow B — when a supplier opens a buyer's profile, the read side joins that table and, if the buyer blocked the supplier, nulls out the buyer's contact and verification fields. There is no queue, consumer, cron or cache.

Business flowchart

Blocking a user, and what it changes

The write is a single upsert; the enforcement is entirely separate:

  1. Both user IDs must be numeric and the flag must be 1 (block) or 0 (unblock), else the whole request is rejected.
  2. One row per (actor, target) pair. A block sets blocking_date; an unblock sets unblocking_date; the other timestamp is preserved, so the full history stays.
  3. Nobody is notified — not the actor, not the target.
  4. On a later Buyer Profile view, if block_status = 1 for buyer → supplier, the response blanks all contact numbers, emails, landline and every verification flag.

Data-flow diagram · Level 1

Where block state is written and where it is read

The two halves never share code — only the table:

  • 1.0 Validate checks numeric IDs, the 0/1 flag, five mandatory fields and IP format.
  • 2.0 Upsert block row writes one row to D1, choosing blocking_date or unblocking_date by the flag.
  • 3.0 Buyer-profile read joins D1 with the matchmaking table D2 in one query.
  • 4.0 Mask fields nulls the buyer's contact + verification fields when the join says the buyer blocked this supplier.

Sequence diagram · Flow A + B

Block, then how it is enforced

The diagram shows a block submit, then a later profile view by the blocked supplier:

  1. The write API validates and runs one upsert; success is decided by string-matching "UPDATE SUCCESS".
  2. Later, the read API's checkMatchMaking query left-joins USER_BLOCKED_STATUS, pulling matchmaking source and block status together.
  3. alt — if the buyer blocked this supplier, the profile response nulls contact + verification fields; otherwise it is returned in full.

The reverse direction (supplier blocks buyer) has no confirmed enforcement point in this codebase.

Glossary

Business terms used above.

The blocking model

Block status
A single flag on the row: 1 = blocked, 0 = unblocked. The same API sets both.
Actor (user_glid)
The user who took the block / unblock action.
Target (blocked_glid)
The user who was blocked or unblocked. Never notified.
blocking_date / unblocking_date
Two independent timestamps. A block updates only the first, an unblock only the second, so both “first blocked” and “last unblocked” survive.
Silent block
No notification is sent to anyone. The target can only infer it if their contact details start showing blank somewhere.
Upsert
One INSERT ... ON CONFLICT (user_glid, blocked_glid) DO UPDATE handles first-time block, re-block and unblock without app-side branching.

Enforcement

Buyer Profile screen
The seller-panel screen where a supplier views a buyer. The one place a block is actively enforced.
checkMatchMaking
The read-side query that left-joins USER_BLOCKED_STATUS with the matchmaking table, returning match source and block status together.
Contact / verification masking
When the buyer has blocked the viewing supplier, all contact numbers, emails, landline and verification flags in the profile response are set to null.
Matchmaking source_id
A separate signal from the same join, indicating how the buyer and supplier are connected. Not part of blocking, but shares the query.

People & access

GLID
GlobalID — the unique internal identifier for one user / company account. Both actor and target are GLIDs.
Gateway allowlist
The ten callers allowed to submit a block / unblock: GLADMIN, SELLERMY, MY, MY1, IMOB, PNS, ANDROID, IOS, ANDWEB, IOSWEB. No role restriction — supplier or buyer can call from any of them.
