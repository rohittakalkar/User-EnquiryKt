Company Logo

A supplier's company logo (four sizes) with a real approval workflow — Pending → Approved / Rejected / Deleted. All four actions go through the single POST /user/logo endpoint, distinguished only by which fields are present. Every change fans out to three replicas: search / IMSDB, LMS, and general company-sync. No supplier email; no cron.

Storefront & Branding

Company Logo

A new logo is always forced to Pending on insert — the supplier cannot publish it directly. Approve / reject is the same endpoint with an APPROVAL_ID present, guarded so it only affects a still-Pending record. Every successful write publishes COMPANY_LOGO_SERVICE; three near-identical consumers each replicate to their own database.

Business flowchart

One endpoint, four actions, a moderation gate

The caller picks the action by which fields it sends:

  • Insert (FLAG=I) — three image sizes are mandatory; status is hard-coded Pending, whatever the caller sends.
  • Update (FLAG=U) — overwrites the images; status becomes whatever the caller passes — it is not forced back to Pending (a gotcha for re-submits after rejection).
  • Approve / Reject (APPROVAL_ID present) — moves a still-Pending record to Approved or Rejected (reason required); a second call on an already-decided record is a silent no-op that still reports success.
  • Delete (FLAG=D) — nulls all four images and the reason, status Deleted.

There is no dedicated logo-read API; the buyer-profile query joins the logo table directly for the 90×90 size.

Where the logo record is written and replicated

One write, a three-way replica fan-out:

  • 1.0 Upsert logo writes D1 for insert / update / approve-reject / delete; approve-reject is guarded by status = 'P'.
  • 2.0 Publish fires COMPANY_LOGO_SERVICE only after a successful DB write.
  • 3.0 / 4.0 / 5.0 are three consumers that each apply the same change to D2 (search / IMSDB), D3 (LMS) and D4 (general company-sync).
  • 6.0 Read joins D1 in the buyer-profile query.

Uploading a logo, then moderation

An insert, then a moderator approval:

  1. The write API checks the gateway (only MY / GLADMIN) and mandatory fields, then inserts with status forced to Pending and returns the approval id.
  2. It publishes COMPANY_LOGO_SERVICE; three consumers replicate the insert in parallel to their own databases.
  3. A moderator calls the same endpoint with the APPROVAL_ID and STATUS=A; the guarded UPDATE ... WHERE status = 'P' runs.
  4. alt — if the record already moved on, zero rows change but the response is still “UPDATE SUCCESS”; otherwise the decision is replicated by the same three consumers.

Glossary

Business terms used above.

Approval lifecycle

Pending (P)
The state a new logo is forced into on insert. The supplier cannot publish a logo directly.
Approved (A)
Set by a moderator; the logo becomes visible to buyers.
Rejected (R)
Set by a moderator, with a mandatory rejection reason. The previous logo keeps showing.
Deleted (D)
A soft-delete — all four image columns and the reason are nulled, the row stays.
One endpoint, keyed by fields
Insert, update, approve / reject and delete all use POST /user/logo, distinguished by FLAG and whether APPROVAL_ID is present.
Guarded approve / reject
The moderation UPDATE only affects a record still at status = 'P'; a second call is a silent no-op that still reports success.
Update does not reset status
On FLAG=U, status becomes whatever the caller sends — it is not forced back to Pending, so a re-submit after rejection can keep a stale status.

Fan-out

COMPANY_LOGO_SERVICE
The queue every successful logo write publishes to, sharded 20 ways by GLID.
Three replicas
Three near-identical consumers each apply the change to their own database: search / IMSDB, LMS, and general company-sync.
Fail queues with no consumer
Two of the three consumers republish failures to _FAIL queues that are not registered anywhere — a silent replica-drift risk.
Publish only on success
The RabbitMQ message is only populated inside the DB-write success branches, so a failed write never fans out.

People & reads

Supplier
Uploads, updates or deletes the logo.
GLADMIN moderator
Approves or rejects a Pending logo. The only two caller types allowed on the endpoint at all are MY and GLADMIN.
No dedicated logo-read API
The logo is read via the buyer-profile query (a direct JOIN for the 90×90 size) and via the search / PDP datasets the IMSDB replica keeps in sync.
Employee-name resolution
When an internal user acts, their UPDATEDBY_ID is resolved to “name (id)” via an extra lookup for the audit trail.
GLID
GlobalID — the unique internal identifier for the supplier the logo belongs to.
