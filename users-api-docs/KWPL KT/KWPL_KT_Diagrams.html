KWPL — Paid Listing Keywords

KWPL (“paid listing keyword”, table PL_KWRD) is an internal record of which keywords, in which city, against which work order, were served to a supplier and for what validity window. It is not customer-facing — only two internal tools may write it, there is no read API, and no queue, cron or notification is attached. One endpoint handles four actions via an ACTION parameter, and every action reports the same success string whether or not a row actually changed.

KWPL — Paid Listing Keywords

POST /kwpl (gateways GLADMIN / WEBERP). ACTION = INSERT (new PL_KWRD row, RETURNING pl_kwrd_id), DISABLE (set the enable flag off), UPDATE (extend validity-end and work order), SEARCH_UPDATE (change only the keyword term). The three mutating actions match only currently-active rows (PL_KWRD_ENABLE = -1 is the “active” sentinel) on (supplier, serve-id), or on the row id for SEARCH_UPDATE. Exactly one meshpg round-trip per request; no rows-affected check.

Business flowchart

A system-of-record for paid keyword placements

Four actions on one table:

  • INSERT — a new paid-keyword placement goes on record: supplier, city, company, keyword, description, from / to dates and a work-order id. It starts active.
  • DISABLE — an active record is switched off when a campaign ends. An already-disabled record is untouched.
  • UPDATE — an active record's validity-end date and / or work-order id are revised, e.g. to extend a campaign.
  • SEARCH_UPDATE — only the keyword term is changed, leaving everything else as-is.

The response says “success” as long as no database error occurs — even when no row matched. There are no notifications and no supplier-facing view.

Where a paid-keyword serve record is written

A single synchronous writer, nothing downstream:

  • 1.0 Validate & branch checks the gateway and the action-specific mandatory fields.
  • 2.0 Write inserts a new PL_KWRD row, or updates an active one, in D1 (meshpg) — one round-trip, no preceding existence check, no rows-affected check.
  • No read endpoint, queue, consumer or cron touches this table.

Sequence diagram · Flows A + B

Creating a keyword-serve record, then disabling it

A create followed by a disable:

  1. An internal tool posts ACTION=INSERT with the full field set; the API checks the GLADMIN / WEBERP gateway and the INSERT mandatory fields, then inserts a new active PL_KWRD row and returns its id.
  2. Later the tool posts ACTION=DISABLE for the same (supplier, serve-id).
  3. alt — an active row matches: its enable flag is switched off. No active row matches: nothing changes, but the response is still “success”.

Glossary

Business terms used above.

The record

KWPL / paid listing keyword
An internal record that a specific keyword was given paid placement for a supplier, in a city, for a validity window, against a work order.
PL_KWRD
The single table this feature writes (“Paid-Listing KeyWoRD”).
Work order id
The internal sales / ops transaction a keyword-serve is billed against.
Serve id
The customer-to-service identifier that, with the supplier id, locates a record for the mutating actions.
PL_KWRD_ENABLE = -1
The legacy “active” sentinel — not 1 or true. DISABLE / UPDATE / SEARCH_UPDATE only match rows in this state.

The actions

INSERT
Create a new active keyword-serve record with the full field set; returns the new row id.
DISABLE
Switch an active record off at campaign end. An already-disabled record is left alone.
UPDATE
Revise an active record's validity-end date and work-order id, e.g. to extend a campaign.
SEARCH_UPDATE
Change only the keyword term of an active record, by row id or by (supplier, serve-id).

Cautions

“Success” is not confirmation
The mutating actions never check how many rows were affected, so a typo'd supplier / serve-id, or an already-disabled record, still returns success.
Internal only
Gateways are limited to GLADMIN and WEBERP; suppliers neither call nor see this.
No side effects
No queue, consumer, cron, email or notification is attached — it is a pure record-keeping write.
No read API
How this data is consumed (a report, a dashboard, direct DB access) is not visible in the codebase.
GLID
GlobalID — the unique internal identifier for the supplier.
