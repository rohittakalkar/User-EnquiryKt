Knowledge Transfer · Engineering

Bizfeed & Recommendation

One pipeline covers Buyer Activity, User Activity and Catalog View: a buyer's browsing is written to a raw clickstream store, a Kafka consumer filters and transforms it into supplier-facing Bizfeed entries, and the supplier can hide or unhide those entries. A separate Recommendation dashboard fans out to four or five internal services in parallel and merges the results into one priority-ranked “action items” list. Not every buyer click becomes a feed entry — four silent filters sit in the middle.

Engagement & Insights

Bizfeed & Recommendation

POST /user/addbuyeractivity (gateways GLADMIN / LEAP) writes im_buyer_activity_attr_v2 (Cassandra). A Kafka consumer (workerUserBusinessFeeds) drops self-views, blocked / fraud / employee buyers, Redis “meeting” matches and over-long GLIDs, then inserts glusr_usr_biz_feeds (Postgres) with a bounded retry. POST /user/bizfeed_hide_unhide toggles biz_feed_is_hidden on a (supplier, buyer, day) match. GET /seller_recommendation fans out to 4–5 HTTP services and always returns all 11 slots.

Business flowchart

Buyer clicks in, supplier insight out

Three cooperating parts:

  • Flow A — capture & transform: a buyer action is stored raw; a background stage then checks four things — is the buyer viewing their own catalog, is the buyer blocked / fraud / an employee, was a recent offline “meeting” logged, is the ID malformed — and only a clean event becomes a Bizfeed entry (with the buyer's city / state attached).
  • Flow B — hide / unhide: the supplier marks a feed entry not useful; the toggle matches on (supplier, buyer, day), so multiple entries for the same buyer on the same day move together. Hiding is a visibility flag, not a delete.
  • Flow C — recommendation dashboard: on open, the system calls company-detail, product-listing, unread-message, Bizfeed and (paid-tier only) credit services in parallel, merges them into a priority-ranked list, and shows an empty slot for any service that failed — the dashboard never errors out.

Data-flow diagram · Level 1

Where activity is captured, filtered and served

A write-optimised store feeding a read-optimised one:

  • 1.0 Activity write appends the raw event to D1 (Cassandra).
  • 2.0 Feed-generation consumer reads block / blacklist / employee / product tables D3 and a Redis key, then inserts D2.
  • 3.0 Hide / unhide write updates D2 on a composite match.
  • 4.0 Recommendation fan-out calls 4–5 external services and merges; it touches no database directly.

Sequence diagram · Flows A + C

A buyer activity becoming a feed entry, and the recommendation fan-out

An activity becoming a feed entry, then a dashboard load:

  1. A buyer action is posted and written straight to the Cassandra clickstream store; a Kafka message follows.
  2. The consumer runs the gates. alt — self-view, blocked buyer, Redis meeting match or over-long GLID: the message is dropped with only a log line; otherwise the buyer's city / state is looked up and a glusr_usr_biz_feeds row is inserted (retried on transient failure).
  3. Separately, the supplier opens the recommendation dashboard.
  4. par — company-detail, product-listing, unread-message, Bizfeed and (if not free-tier) credit services are called at once; results merge into 11 priority-ranked slots, empty ones defaulting to a zero count.

User Activity, Buyer Activity and Catalog View are one pipeline on one table; the Kafka producer and the Redis “meeting” key's writer sit outside the three repos. The block-gate is fail-open, hide / unhide has no row-level granularity, and the PayIM recommendation slot is always empty — all flagged in the source doc.

Glossary

Business terms used above.

The pipeline

Buyer Activity
A captured buyer interaction — a search, a product view, a category browse. Written raw first, filtered later.
Clickstream store
A high-write Cassandra table (im_buyer_activity_attr_v2) holding every raw event, append-only.
Bizfeed
The supplier-facing feed of “a buyer viewed your product, from this city” entries, generated from clean activity events.
Feed-generation consumer
A Kafka worker that transforms raw events into glusr_usr_biz_feeds rows after running the filters.
Catalog View / User Activity
Other names for events on the same pipeline and table, distinguished by an activity-type id.

The four filters

Self-view
A supplier viewing their own catalog never generates a feed entry.
Block gate
Disabled, blacklisted (by mobile / email / domain), invalid-mobile or internal-employee buyers are dropped. If the gate's query errors, the event is let through (fail-open).
Meeting bypass
If a Redis key for the buyer exists — taken to mean a recent offline sales meeting — the event is dropped as redundant.
GLID length
A buyer or seller id longer than 10 digits is treated as invalid data and dropped silently.

Hide & recommend

Hide / unhide
A visibility toggle on feed entries. 1 hides; 0 clears the flag (stored as NULL). Data is never deleted.
(supplier, buyer, day) match
The only match key the toggle has; several entries for one buyer on one day are hidden or shown as a group, not individually.
Recommendation dashboard
An aggregator that calls company-detail, product-listing, unread-message, Bizfeed and credit services in parallel and merges them into one ranked list.
Free-tier re-ranking
For a free-tier supplier the credit service is skipped and the remaining items are re-prioritised (profile / GST completeness rises).
Always-complete response
All 11 recommendation slots are always present; a failed or suppressed service yields an empty slot with a zero count, never an error.
GLID
GlobalID — the unique internal identifier for a buyer or supplier.
